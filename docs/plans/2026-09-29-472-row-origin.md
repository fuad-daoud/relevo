## 1. How it works today (file:line)

- **One DB per machine** (D8). `relevo serve` stores each client's rows in the same `relevo.db`, scoped by `owner`: `store.NewShared(root, owner, d)` (`internal/store/store.go:95-97`), called from `Server.ownerStore` (`internal/serve/serve.go:134-141`). Here owner is the enrolled client key id (`ownerIDOf`, `:127-130`).
- **`owner` is relative.** `''` means "this machine" (`003_binding_record.sql:18`). The live uniqueness key is `(owner, name) WHERE archived_at IS NULL` (`005_owner_scope.sql`). Every record call filters on owner only (`record.go:89, 101, 117, 159, 180, 218, 229, 239`). No table has a machine or installation column.
- **A remote binding exists as two rows that do not reference each other.**
  - The client's row is `owner=''` with `Builder.Mode=remote` and `Server=<name>` (`remote_add.go:297-339`).
  - The server's row is `owner=<client id>`, created in `handleCreateBinding` (`internal/serve/bindings.go:100-134`).
  - `BindingView` (`internal/remote/proto.go:150-212`) carries no id and no server identity. `WhoAmI` (`proto.go:73-`) returns the *client's* id and label, never the server's.
- **Tables that allocate counters:**
  - `binding_event.seq`: per record (above).
  - `config_revision.rev`: an INTEGER rowid alias (`006_config_revision.sql`; `revision.go:46-57`).
  - `config_meta.version`: a singleton (`002_config.sql`; `config.go:68-97`).
  - Mirror `round(binding_id, number)` and `transcript(owner_kind, owner_id, seq)`: both keyed under ULID parents.
  - Mirror `binding`: natural key `(name, created_at)` (`write.go:246`; `001_initial.sql` `binding_name_created_at_uidx`), with a fresh ULID id (`write.go:267`).
  - `repo`: `UNIQUE(origin_url)` and `UNIQUE(common_dir)` (`001_initial.sql`), with a fresh id (`write.go:96`).
- **Everything in the file syncs.** Turso's Go SDK cannot exclude tables (`compression-spike.md:124-131`). That covers `kv`, `secret` (which holds `client.key`) and `mastermind` pids, all of which are machine-local by nature.
- **A value in the DB is not machine-unique.** `db.SetFreshTemplate` / `seedFromTemplate` (`internal/db/template.go:18-57`) copies one DB file into every fresh test DB, and `BackupTo` (`db.go:186`) copies the whole file. A hostname is not unique either: the laptop and zen share the hostname `zen` (memory).
- **Who opens the DB:**
  - `store.dbForWrite` → `db.Open(s.DBPath())` (`internal/store/db.go:19-43`; `DBPath` at `internal/store/paths.go:273`).
  - `cmd/relevo/wire.go:221-226` `openDB`.
  - The server's `cfg.DB`.
  - `db.Options` (`db.go:53-60`) already threads per-open settings through.
- **The daemon's run-once start passes** are `ingest.DedupeMirrorOnce` and `db.CompressHistoryOnce` (`cmd/relevo/daemon.go:183-215`). Each records itself in `kv`.

## 3. Installation id: the decision

- **Where the id lives: `<state root>/installation.json`, a plain file.** It holds `{"id": <ULID from db.NewID>, "label": <string>, "created_at": ...}`, mode 0600, created with `O_EXCL` so a racing first open keeps one winner.
  - It cannot live in `kv`. Last-push-wins would make every installation read the same key after sync, and a DB copy, backup or template would clone it.
  - It is not a new place for config either: it sits next to `relevo.db` under `store.DefaultRoot()` (`store.go:110-121`), so it is state, not config (`userConfigRoot()` does not apply).
  - When the local-only DB arrives, the file's contents move there (item 4's machine-local scope).
- **The label defaults to the hostname.** It is display-only. Uniqueness comes from the id alone, which matters because the laptop and zen share a hostname.
- **A synced directory table, `installation(id PK, label, first_seen, last_seen)`, is added in migration 014.** Each installation upserts only its own row, so other machines can show a label after sync. The row is a projection of the file; the file is authoritative.
- A new package `internal/installation` (one concept) exposes `Load(root) (Installation, error)`, which mints the file when it is absent.

## 4. Link between the client and server copies

- **Wire changes (all additive, advertised as `remote.FeatureOrigin = "origin"` in `proto.go:318-361` and in `handleWhoAmI`'s feature list, `internal/serve/routes.go:99-108`):**
  - `WhoAmI` gains `Installation string` (the server's installation id) and `InstallationLabel string`.
  - `BindingView` gains `ID string` (the server's `binding_record.id`) and `Installation string` (the server's installation id). `ServedView` fills both (`internal/relevo/served.go:85-160`). Every serve handler already builds its view through `ServedView` (`bindings.go:133, 258, 294, 380, 464, 508`; `rounds.go:99, 384`; `roundfiles.go:259`).
  - `CreateBindingRequest` (`proto.go:102-`) gains `ClientInstallation string` and `ClientBindingID string`. The client **pre-mints** its record id before calling `CreateBinding` (`remote_add.go:236`), so both sides know each other's id from the start. `insertRecord` already honours a caller-set `r.ID` (`record.go:196-200`).
- **What each row stores:** two promoted columns on `binding_record`, `link_origin TEXT` and `link_id TEXT` (nullable).
  - The client row stores (server installation, server record id).
  - The server row stores (client installation, client record id).
  - Promotion follows the existing pattern: `store.Binding` gains `Link *RemoteLink{Installation, ID}` (json `link,omitempty`), and `prepareSave` (`lifecycle.go:162-`) promotes it into `db.Record`. `RecordPut`'s UPDATE and INSERT (`record.go:184, 205-209`) write the columns.
  - Per the rule at `internal/store/format.go:8-20`, this is a field `recordFormat` does **not** stamp. An older binary that drops it loses only the link, so `BindingFormat` stays 10. The builder states this in the report.
- **The server record id** is exposed from `store` for the running binding, e.g. `Store.RecordID(name)` next to `ArchivedBinding.RecordID` (`internal/store/archive.go:12, 59`). The server needs it for `ServedView`.
- **How duplication stops (reader in the sync round, not built now):** a cross-origin binding list collapses any pair where row A's `(link_origin, link_id)` equals row B's `(origin, id)`. The row with `owner=''` (the client's, which the MasterMind drives) is shown, and the server row is attached as its execution copy. This pass only guarantees that the columns are filled on both sides for every binding created by a new client against a new server.
- **Old peers and existing rows:**
  - An old server omits the new fields, so the client row gets `link = nil`.
  - An old client sends no `Client*` fields, so the server row gets `link = nil`.
  - Existing remote bindings stay unlinked. There is no backfill; an optional one is an open question.

### Slice B: `origin` columns, scoping and uniqueness (steps 3-5)
- **014 continues:**
  - `ALTER TABLE binding_record ADD COLUMN origin TEXT NOT NULL DEFAULT ''`.
  - `ALTER TABLE binding ADD COLUMN origin TEXT NOT NULL DEFAULT ''` (the ingest mirror).
  - `ALTER TABLE repo ADD COLUMN origin TEXT NOT NULL DEFAULT ''` and `ALTER TABLE mastermind ADD COLUMN origin TEXT NOT NULL DEFAULT ''` (A3; `planner` was renamed to `mastermind` by migration 008).
  - Drop `binding_record_owner_name_uidx` and create `binding_record_origin_owner_name_uidx ON binding_record(origin, owner, name) WHERE archived_at IS NULL`.
  - Drop `binding_name_created_at_uidx` and create it again on `(origin, name, created_at)`.
  - Re-key the mirror uniqueness by origin (A3): `repo (origin, origin_url)`, `repo (origin, common_dir)`, `mastermind (origin, harness_kind, session_id)`.
  - Add a plain index on `binding_record(origin)`.
- **Child rows inherit origin through their parent:** `binding_event`, `round_file` (via `record_id`), and mirror `round`/`event`/`artifact`/`transcript` (via `binding_id`/`round_id`, and for `transcript` via its `owner_id`). They get no column. This is stated in the migration header.
- **Rule for rows written before 014 (stated once, in `record.go`):** `origin = ''` means "written before 014 by this installation".
  - Every scoped read and write filters `origin IN (?, '')` with the DB's origin. This covers `getRecord`, `RecordList`, `RecordListArchived`, `RecordGetArchivedByName`, `RecordPut`'s select, `RecordArchive`, `RecordDelete` and `RecordSetViewed` (`record.go:87-244`).
  - Every insert stamps origin. `RecordPut`'s UPDATE also sets `origin = ?`, so any row it touches is stamped.
  - A DB opened with `Origin == ""` (tests, the peek runtime) behaves exactly as today: the filter becomes `origin = ''`.
  - `RecordGetByID` and `RecordCounts` stay unscoped.
- **Mirror:** `UpsertBinding` (`write.go:232-282`) adds `origin` to its natural-key select and to its insert; `UpsertRepo` and `UpsertMasterMind` do the same for their natural keys, and the same for the lookup that refuses a second id for one session key (A3).
- **One-time backfill, done by the daemon:** `db.BackfillOriginOnce(d, origin, now)` runs next to `DedupeMirrorOnce` (`daemon.go:190`).
  - It runs `UPDATE binding_record SET origin=? WHERE origin=''` and the same on `binding`, in one transaction.
  - It records itself in `kv` the way the other passes do. No backup is needed: the update is additive and reversible to `''`.
  - It is not run in `db.open`, because open-path writes failed under load (`db.go:131-134`).
  - Until it runs, the `IN (?, '')` rule keeps every old row visible.
  - **The sync round must refuse to run while any `origin = ''` row remains.** This is a hand-off, stated in the report.
- **Paths pair with origin (A2).** Path values stay absolute and are never rewritten; every read pairs the value with the row's `origin`, and when the origin is not the local installation, a surface shows the value with that installation's label and never opens it. The full list of path columns (`binding.cwd`, `binding.worktree`, `binding.archive_path`, `binding_record.cwd`, `repo.common_dir`, `planner.transcript_locator`, `event.path`, `ingest_cursor.source`, `config_import.source_path`), `record_json` fields (`cwd`, `worktree`, `repo_ref.common_dir`, `builder.log_path`, `serve.bare_repo`) and `kv` values (`daemon.exe`, `serve.daemon.root`) is in `SCOPES.md`. No code for this in the round beyond the document.
- `repo` is **not** given a shared identity across installations in this pass (open question 2); it is per-origin, one row per installation, and rows are never merged across origins.

## 9. Open questions for the user

These stay open for the sync round (A5). A1 records the current leaning on
question 1; A3 takes the first branch of question 2 for this round (add
`origin`, re-key the indexes) without deciding identity across installations.

1. **Does config sync?** `config_doc`, `config_revision` and `config_meta` hold per-machine candidates: zen's harnesses are not the laptop's. My proposal is that config is machine-local and goes to the local-only file. That would make the counter item moot.
2. **`repo`:** keep it per-installation (add `origin` and re-key `UNIQUE(origin, origin_url)`), or treat it as shared with `common_dir` moved out? `common_dir` is a local path. Right now two machines inserting the same `origin_url` collide on sync.
3. **`secret`'s `client.key`:** if it syncs, two installations share one client identity on every server. Should the sync round require the local-only file before the first sync?
4. **Old remote bindings:** backfill their links through a `GetBinding` sweep, or let them age out?
5. **The label:** is the hostname acceptable as the default given the laptop/zen collision, and should `relevo config` edit it?
