# Chains slice 1 · round 5b — repair before the reviewer, and the member sweep

One-shot builder round. It starts from a branch where rounds 1-5a and 8 are merged, and runs in parallel
with round 7 (`show --trace`, `wait`) on another builder; the MasterMind merges the two afterwards, and
the slice lands as one PR. Commit, never amend. Ends with `make check` green.

## Deliverable

A red gate first spends the member's own repair budget (the gate repair loop `startRepairRound`
already runs): while the extracted `repairDecision` allows another repair, the chain raises no event,
writes no trace row and keeps awaiting the builder on its new round; when the budget is spent or the
failure is unchanged, the event goes red to the reviewer. The daemon also sweeps running chains: a
member whose record is gone or that sits NEEDS YOU halts the chain with that member's reason.

## Pinned behaviour

- **Repair before the reviewer.** On a builder close with a red gate and a repair budget that can
  still run (`gateSignature` + the extracted `repairDecision`), the chain does not raise an event:
  `startRepairRound` runs, the chain's awaiting moves to the new builder round, and only the chain row
  is saved (no trace row). When no repair can run (budget spent or the gate output unchanged), the
  event is raised with gate red and the reviewer sees the check output. A member halt inside that path
  halts the chain with the member's reason. The repair round is a member round like any other: its
  output is consumed, and its own close is the next event the chain maps (green, or red once the
  budget is spent, → the reviewer).
- **One place opens a repair.** Only `markerClose` opens a repair round, in today's order (after
  `clearProcess`), so no close path can clobber a just-opened round. `chainApply` only decides and
  moves `Awaiting`; `markerClose` acts on the same decision. A `startRepairRound` that fails to start
  leaves the member NEEDS YOU as today, and the sweep below halts the chain with the member's reason.
- **Sweep** (`tickChains`). For every chain with status running, load each member; a member whose
  record is gone halts the chain with `member <name> gone`; a member in NEEDS YOU halts it with the
  member's reason. Runs under `rt.Store.WithLock`, once per tick, through `d.safely` like the other
  non-binding phases. A halt goes through `chainTerminal` (status + one trace row + the one end
  delivery), so a second tick writes nothing more.
- **No trace row for a repair.** The repair is not a chain transition: the phase, step, plan and
  corrections stay as they were, only `Awaiting` changes.

## Carry-over from round 5a's review (do this first)

A mutation survived 5a's tests: deleting `next.Awaiting.Round = sent.Round` in `chainApply`
(`internal/relevo/chain.go`) leaves every `TestChain*` green, because in every fixture the next member's
round happens to equal the stale round `Next` left in `Awaiting`. In a real chain the members' round
numbers diverge (after one correction the builder is on round 3 while the reviewer is on round 2), and a
stale round would make the chain ignore the reviewer's close forever.

1. `internal/chain/chain.go`: `send()` sets `s.Awaiting.Round = 0` along with the member, so a caller that
   forgets to fill the round can never match a stale one. Update any `internal/chain` test that asserted
   the old round survived a send. (`internal/chain` joins this round's scope for this line and its tests.)
2. `internal/relevo/chain_test.go`: add `TestChainAwaitsTheSentMembersOwnRound`. Build a chain whose
   members' rounds differ (for example the reviewer already has 3 closed rounds, the builder 1): after
   the builder's close, the chain row's awaiting round is the reviewer's new round, and a close of that
   round advances the chain. It must fail when `next.Awaiting.Round = sent.Round` is deleted; run that
   mutation and say so in the report.

  still awaits the builder, no trace row, nothing pending).

## Halt conditions

- If `repairDecision`'s bounds cannot be shared with `startRepairRound` without changing its halt
  wording (repair.go:104-109), halt; the repair tests pin those strings.
- If the close has not advanced the binding by the time `queueReport` runs (so `b.Round` is not the
  repair round's number), halt and report: `Awaiting` would name the wrong round.
- If the builder member's `RepairCount`/`Regate`/`LastGateSig` bookkeeping cannot be read at the
  red-gate decision point, halt.
- If `Daemon.Tick` cannot run `tickChains` before its `len(bindings) == 0` early return (daemon.go:158),
  halt and report the phase placement.
