## Plan B2: `relevo doctor` muse rows

Behaviour: doctor reports, for muse, the plugin installed, enabled and
approved (hooks and MCP), and its version against relevo's, mirroring the
Claude plugin rows' wording and fix hints:

- `muse plugins marketplace add relevo https://github.com/fuad-daoud/relevo.git`
- `muse plugins install relevo@relevo`
- `muse plugins approve relevo`
- `muse plugins update relevo`

The fact source (muse's plugin state on disk vs `muse plugins inspect relevo
--json`) is whichever the builder proves reliable on a muse install; doctor
tests must never spawn `muse`, so the probe goes through an injected reader
(`doctor.Env.Command`, which `fakeEnv` already answers via `commandFn` in
`internal/doctor/doctor_test.go:49,127`, or a small reader func on the input).

Cases:

- No muse binary on `PATH` and no muse record: no muse rows at all (same shape
  as the Claude gating today).
- Plugin state readable and relevo plugin present, enabled, approved, hooks
  and MCP active, versions matching: rows OK.
- Plugin missing: FAIL with the marketplace-add/install fix.
- Plugin present but not enabled: FAIL with the enable fix.
- Plugin present but not approved (hooks/MCP inactive): FAIL with the
  `muse plugins approve relevo` fix.
- Version mismatch: Warn with the `muse plugins update relevo` fix, advisory
  only like the Claude version row.
- Unreadable/unparseable state: `not checked` OK rows, never FAIL.
- `MUSE_SESSION_ID` set (read directly with `os.Getenv`, not via `Detect`):
  the session row resolves like the Claude MasterMind row; note the dependency
  on the parallel `Detect` branch in a comment pointing at `ident.go`.

### Probe answer (measured by the MasterMind on Muse Code 1.4.11; use this, do not re-probe)

Use `muse plugins inspect relevo --json` (through the injected `doctor.Env.Command`). The on-disk files cannot tell approval: `$XDG_CONFIG_HOME/muse/settings.json` `runtime_capabilities` stores only trusted definition hashes, and whether they still match the installed package is muse's computation. Shapes:

- Not installed: exit 1, stdout `{"error":{"code":"unknown-plugin","message":"plugin `relevo` is not installed"}}`.
- Installed: exit 0, a JSON object with `active` (bool), `record.enabled` (bool), `record.version` ("0.22.4"; also `plugin.version`), and `runtime_capabilities`: an array of `{"candidate":{"kind":"hook"|"mcp_server"|"invocation_preapproval","stable_id":"plugin:relevo:hook:hook-...","plugin_id":"relevo",...},"status":"...","diagnostic":null}`.
- Approved: every `hook` and `mcp_server` capability has `status` `trusted_enabled`.
- Installed but never approved: those capabilities read `review_needed` (they also read so after `muse plugins update relevo` changes a definition).
- Rejected one: `trusted_disabled`.
- Disabled plugin (`muse plugins disable relevo`): `active` false, `record.enabled` false, `runtime_capabilities` an empty array. Fix: `muse plugins enable relevo`.

So: not installed -> FAIL install fix; `record.enabled` false -> FAIL enable fix; any hook or mcp_server status other than `trusted_enabled` -> FAIL `muse plugins approve relevo` fix (name the statuses seen); `record.version` != relevo's version -> Warn update fix; spawn error or unparseable JSON -> `not checked` OK. B2 step 1 (the probe note) is done: skip it.
