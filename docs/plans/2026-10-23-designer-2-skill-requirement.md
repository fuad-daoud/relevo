# Plan 2: The actor names the skill it needs; resolution; doctor row

**Prerequisite**: Plan 1 is already committed on this branch by the previous round (this plan edits the `designer` shipped-table row Plan 1 creates; setup seeds no designer actor, so a designer actor exists only where a user added one).

**Goal.** An actor can declare the skill(s) it needs (`skills`, default `design-runbooks` for the shipped `designer`); a pure function says where each harness kind looks for a skill and whether it is there; `relevo doctor` FAILs, with the paths it looked at, when a candidate of such an actor cannot resolve it. The pick is Plan 3.

**Behaviour and cases.**
- Actor JSON gains `"skills": ["design-runbooks"]` (optional). Names must match the agent-name pattern (`^[a-z0-9][a-z0-9._-]{0,63}$`) and be unique. A designer actor without the field needs `design-runbooks`; a designer actor with `["other-skill"]` needs only `other-skill`. Any shape may declare skills; other actors need none.
- Locations (project first, then user), per harness kind, always `<name>/SKILL.md` under:
  - claude: `<repo>/.claude/skills`, `~/.claude/skills`
  - opencode, agy: `<repo>/.agents/skills`, `~/.agents/skills`
  - codex: `<repo>/.agents/skills`, `~/.agents/skills`, `~/.codex/skills`
  - any other kind: not servable.
  `<repo>` is the directory the caller passes (the doctor's working directory; Plan 3's binding directory). An empty `repo` skips the project paths and says so; a skill found at the project path wins over the user path.
- Doctor: for every actor whose effective skills are non-empty, for every distinct harness kind among its on-or-off candidates the registry ranks, one row per (kind, skill): OK with the found path, or **FAIL** `skill design-runbooks for designer on claude not found: looked at <p1>, <p2>` with the fix `install the skill at <p1> or <p2>`. A kind that cannot see skills at all FAILs with `<kind> cannot load skills`. A doctor run outside any directory it can resolve still checks the user paths.
- Known limitation, stated in the report and README: accounts with their own per-process home (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) are checked against the default home only.

**Steps.**

1. **The resolver.** Create `internal/skill`: `Locations(kind, name, repo, home string) []string` returning the ordered SKILL.md paths for the table above (project paths omitted when `repo` is empty), `Servable(kind string) bool`, and `Resolve(exists func(string) bool, kind, name, repo, home string) (found string, looked []string)`. Table-driven tests: every kind's order and exact paths, project beats user, an empty repo skips project paths, an unknown kind is not servable and has no locations, a skill present only at the user path of a second location (codex `~/.codex/skills`) resolves. Verify: `go test ./internal/skill`.
2. **Config field.** `Actor.Skills []string` with `json:"skills,omitempty"`; `validateActor` rejects a name that fails the agent-name pattern and duplicates (error wraps `ErrBadActors`, text `actors: <name>.skills[i]: ...`). `ShippedAgent` gains `Skills []string`; the `designer` row sets `Skills: []string{"design-runbooks"}`. Add `EffectiveSkills(agent string, declared []string) []string` beside `Shipped` (declared non-empty wins and is copied; else the shipped agent's default copy; else nil), mirroring `EffectiveOutputs`. `rowFor` sets `Row.Skills = EffectiveSkills(actor.Agent, actor.Skills)`; `Row.Skills` (`json:"skills,omitempty"`) is validated like the actor field; `buildFile` copies it into `Role.Skills`, and `copyRole` deep-copies it. Verify: `go test ./internal/roles` with tests for: the default on a bare designer actor, the override, a bad name, a duplicate, the unknown-key list still empty for a `skills` key and non-empty for `skill`, and the Role copy being independent of the registry's own slice.
3. **Doctor rows.** `internal/doctor/skills.go`: `type SkillNeed struct{ Actor, Kind, Skill string }` and `SkillChecks(env Env, repo string, needs []SkillNeed) []Check` using `skill.Resolve` with `env.Stat` as `exists` and `env.HomePath("")` for home (a `HomePath` error yields one `ProbeFailed` warn row, as `roleCheck` does). Rows: Group = kind, Name = `skill <name>`, severity OK / FAIL per the cases above, detail naming the actor and the paths. `cmd/relevo/doctor_skills.go` builds the needs from `rt.RoleRegistry()` roles with `Skills` and the harness kinds of their `Ranked` candidates (resolve each token through `rt.Candidates`), deduplicated and sorted, and passes `os.Getwd()` as `repo`; `cmd/relevo/doctor.go` gets one line appending the rows next to `roleSourceChecks`. Verify: `go test ./internal/doctor ./cmd/relevo -run 'Skill|Doctor'`, with doctor tests for present at project path, present at user path only, absent (FAIL lists every path looked at), a kind that cannot load skills, and the `HomePath` failure.
4. **README**: document `actors.<name>.skills`, the default for `designer`, the location table, the doctor row and the account-home limitation. Verify the diff is only those edits.
5. **Gate**: `make check-affected`. Verify exit 0. (The new package starts without a coverage baseline; CI's coverage job reports it. If `testdata/coverage-baseline.txt` needs a line for `internal/skill`, run `sh scripts/check-coverage.sh --write` and say so in the report; never lower an existing number.)
