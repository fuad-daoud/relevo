## Where the two remote facts come from

- **The plan-start commit of a remote member** is the head of the client's own `relevo/<name>` branch at the send — the exact sha the ship publishes as `refs/relevo/<name>/out`, which the server merges into its served branch (`syncRoundWorktree`, `internal/serve/rounds.go:246`), so it is the commit the server's next round is cut from. Plan 1's start is already recorded as `base.commit` (the branch's cut point). Every later plan's start must arrive on `sent`; #779's assignment reads `sent.RoundBaselineHead`, so `chainSendMember`'s staging arm records `RoundBaselineHead` = the `rt.Git.RefSHA` of `refs/heads/<branch>` before it returns. The read is a local ref lookup, not a network call.
- **The closed tree of a remote member** is the pulled result commit: the catch-up absorbs the server's branch into the client's `relevo/<name>` (`absorbCatchUpBundle`, `remote_bundle.go:109-159`) and the view carries the head it closed at (`view.ResultCommit`, `internal/relevo/served.go:78-96`). `applyCatchUp` (`remotefetch.go:492-537`) records it on the member beside `b.Builder.LastKnown` (`:520`): `b.RoundClosedTree = view.ResultCommit`. `queueReport`'s advance must not wipe it: the client's own diff capture never runs for a remote round (the catch-up wrote the diff entry from the view, so `HasEntry` skips the capture) and there is no local worktree to snapshot. The value is a commit, not a tree: `capture.PlanDiff` hands it to the same `DiffTrees`, and `git diff` accepts a commit as a tree-ish; the local end is a tree only because a local snapshot produced one. Nothing but the chain's `chainPlanDiff` reads a remote binding's closed tree (drift and the verify consult are local-only), and a chain member's server always sends a result commit because the placement probe refuses a server without `chain_member`.

Both facts land in the client's own repo (`addRemote` sets `CWD: opts.Repo`, `remote_add.go:325`), so `chainPlanDiff`'s `DiffTrees(dir=b.CWD, from=plan_start_commit, end=pulled commit)` runs entirely on objects the client holds.

## Deliverable

A remote builder's close reaches the chain with its real gate result and its fetched log on the report entry, so #779's `chainSeedView`/`chainRoundGate` fill the reviewer's check line and log path with no seed code here; a stopped remote round raises the chain's `stopped` event; the member's pulled result commit is recorded as its closed tree and each remote send records the branch head as its round's baseline head, so `plan_start_commit` and the plan's cumulative diff reach the reviewer; a red gate on a remote member stages the chain's own repair round (with the chain's own budget) for the pending-send step to ship, and a red gate whose budget is spent still reaches the reviewer; a correction or fix plan reaches the remote builder as the text #779's `chainSeedText` returns, staged by the pending-send step, never started locally.

## Pinned behaviour

- The gate record on a remote close is the view's result with the locally fetched log path; a remote round whose server ran no check reports no result, the record stays nil, and the close is `chain.GateNone` — the reviewer's seed says `No check ran for this round.`, never green.
- The seed's check line, judged builder round, plan-cumulative diff and round prompt come from #779's `chainSeedView`/`chainRoundGate`/`chainPlanDiff`/`chainRoundPromptPath`; this round only puts the record, the pulled tree and the plan start where they read them. No new seed field and no new round_file-key path is added to a seed.
- A remote member's `RoundClosedTree` is the pulled result commit of its last closed round, recorded when the catch-up proves the round is home (after the absorb, before the report), and it survives the close's advance; the local snapshot's assignment stays byte-identical for every non-remote binding.
- A plan started on a remote member records `plan_start_commit` = the head of the client's `relevo/<name>` branch at the staging, through #779's existing assignment; a correction, a repair and a resume change nothing.
- The `stopped` argument reaches only the chain event; the stop note and the `stopped/…` entry keep their stored-request rules.
- The reviewer's prompt is rendered in the same critical section that installed the pulled files, so every path it names exists before the round is sent.
- A remote red gate is the chain's to spend, on the *client's* member record (`Regate`, `RepairCount`, `LastGateSig`), because the served binding never opens a repair; the staged repair round's prompt entry carries the chain's step note (`chain builder`), not `repair k/M`, and the staged text itself carries the repair fact.
- A later builder round for a remote member — plan 2, a correction, a fix plan or a repair — is staged, never started locally; the pending-send step ships it with verify off.
- A remote round collected without a gate result that the server cannot report (a pre-`chain_member` server) is unreachable: the placement probe refuses such a server at start.
