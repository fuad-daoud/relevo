## Rule applied to every wait

- A wait for a condition ends when the condition holds or the test binary's own
  deadline arrives. It does not end at a guessed 5/10/15 s.
- A timeout that only decides *how a failure shows up* (`select` with
  `time.After(5*time.Second)` on a channel) is deleted. `go test -timeout` and
  its goroutine dump already do that job.
- A time bound that *is* the property (the client returns within its grace) is
  not touched here; see "Left alone".
- Lower bounds ("waited at least X") cannot flake on a slow machine and stay.

## 1. Shared helper: poll until the condition or the test deadline

Seam: `internal/db/helpers_test.go`, new `pollUntil(t, cond func() bool, msg string)`.

- It sleeps in short steps. It stops at `t.Deadline()` minus a small margin and
  fails with `msg`. With no deadline set it polls forever.
- It replaces these fixed-deadline loops:
  - `waitFor` in `poolbound_test.go:~122` (10 s).
  - `waitForPath` in `reexec_test.go:~50` (10 s).
  - the ready-file loop in `openlock_test.go:~165` (`startLockHelper`, 10 s).
  - `waitOwnerConns` in `cancel_test.go:~86` (15 s).
  - the 5 s rollback loop in `protocol_test.go:~180-195`.
- Child-process waits also stop when the child exits. `waitForPath` and
  `startLockHelper` take an `exited <-chan struct{}`. The test starts a goroutine
  that runs `cmd.Wait()` and closes it. A dead helper then fails at once with
  `msg` instead of waiting out a deadline. Update both callers of `waitForPath`
  (`reexec_test.go`, `reexec_reap_test.go:83-91`) and the `Cleanup` that kills
  the child.
- Deliverable: one helper, no remaining `time.Now().Add(<n> * time.Second)`
  loop in those files. Check: `grep -n "Now().Add" internal/db/*_test.go` shows
  only intended uses.
- `waitOwnerConns` and `waitFor` keep their signatures so their callers do not
  change.

## 2. `TestReexecNewImageOpensTheDatabaseAtOnce` (`reexec_test.go`)

- **Pins today:** the exec'd image closes its open-lock fd, so the next image
  opens with `openLockWait = 0` and succeeds. A surviving lock makes the helper
  exit 1, so `opened` never appears.
- **Cause:** `waitForPath` gives each stage 10 s. Starting a fresh test binary
  and opening Turso on a loaded macOS runner can exceed that. The 10 s pins
  nothing; the property is carried by `openLockWait = 0` in the helper.
- **Rewrite:** Step 1's `pollUntil` + `exited` channel. A helper that dies, which
  is what a surviving lock produces, fails immediately with the existing
  message. Otherwise the wait is unbounded except by the suite's deadline. The
  assertions are unchanged.
- **Not changed:** the reap-test's `time.Sleep(500 * time.Millisecond)` before
  counting reap lines (`reexec_reap_test.go:~107`) is a "nothing more happens"
  wait that cannot be made exact; see "Left alone". Only its `waitForPath`
  calls change.
- **Mutation:** set `openLockWait = 0` to a nonzero wait in the helper, or keep
  the previous image's lock fd open across the exec. The test must fail by the
  helper exiting, not by a timeout. Name the failing test in the report.

## 3. `TestDirectHandlesOnOneFreshPathWriteTogether` (`db_test.go:236-330`)

**Pins today:** two direct `Open`s of one fresh path race first-page creation,
and the creation gate in `handles.go` (`created` channel) must serialise them.
Then 2×25 concurrent `Tx` inserts must leave 50 rows and `integrity_check=ok`.
It runs 30 iterations because the corruption is probabilistic.

**Why it is slow (hypotheses, in order of likelihood; measure before coding):**

A. Busy backoff dominates. `DB.tx` (`db.go:~405-425`) sleeps a random 25-100 ms
   after each busy `BEGIN IMMEDIATE`. Two handles hammering one write slot
   collide on nearly every insert. 1500 inserts × a fraction of collisions ×
   ~62 ms would give the observed ~50 s, and load stretches every sleep.

B. Fresh-file cost dominates. Each iteration builds and migrates a new file
   (two `Open`s, schema creation, `integrity_check`) and the 30 iterations run
   serially.

**Step 3a (diagnose):** temporarily instrument locally and never commit it.
Time each phase for 3 iterations (`openFreshPair`, `writeThroughBoth`,
`assertProbeIntact`). Count busy `BEGIN` retries in `DB.tx` with a counter. Run
once under the default mode and once with `RELEVO_DBTEST_OWNER=1`. Report the
numbers in the PR.

**Step 3b (fix by outcome):**
- If A holds, add one seam in `db.go` next to `beginRetryFor`: an unexported
  package var `beginBackoff` of func type returning the sleep duration. The
  default keeps today's `25 + rand.Intn(76)` ms. This follows the existing
  precedent of `busyTimeoutMS` and `beginRetryFor`, which tests already override.
  The test sets it to ~1 ms and restores it in `t.Cleanup`. This changes
  nothing the test pins, which is creation and WAL integrity, not the backoff
  length. It keeps all 30 iterations. Keep the production line count of
  `DB.tx` within 70 lines (check; extract the sleep if needed).
- If B holds, run iterations as parallel subtests of one parent
  (`t.Run` + `t.Parallel`, bounded to 4 by a semaphore). The parent waits, so a
  global override is safe, and no new top-level `t.Parallel` is introduced.
  Keep 30 iterations.
- If neither explains more than half the time, stop and report the measurement.
  Do not shrink the iteration count to get speed.

**Mutation:** in `handles.go`, bypass the `created` wait. The test must fail
across its 30 iterations, either an `Open` error or a wrong row count or
`integrity_check`. Report how many of 20 runs of the mutant fail. Compare with
the pre-change test run against the same mutant; the rewrite must not catch
fewer.

**Done when:** alone, the test takes under about 10 s on the builder's machine;
the report gives before/after wall time.

## 4. `TestCancelledExecIsNotRetried` (`cancel_test.go:19-72`)

**Pins today:** a call cancelled on the wire returns the caller's own
`context.Canceled`, never `driver.ErrBadConn` (which `database/sql` would
retry, applying an INSERT twice), and the row count ends at most 1.

**Cause:** the statement is a 1,000,000-row recursive CTE and the cancel fires
after `time.Sleep(50ms)`. On a fast runner the statement finishes before 50 ms,
or the owner's reply lands inside the client's 250 ms `cancelGrace`
(`wire/client/session.go:50`); the reply then wins and `ExecContext` returns nil
("cancelled insert returned success"). A slow runner makes the cancel land
before the request is on the wire, so nothing is pinned.

**Rewrite (deterministic hold instead of a race against speed):**
- Serve the owner's database `d` with `OpenWith(path, Options{BusyTimeout: 2 minutes})`.
  Hold its write lock from the test with an open `BEGIN IMMEDIATE` on a dedicated
  conn, so the owner's INSERT blocks in the engine for as long as the test
  wants. Use a trivial INSERT instead of the CTE.
- Sync point: `pollUntil` on `d.sqlDB.Stats().InUse` rising above the test
  holder's connection, which means the owner has pinned a connection for the
  request. The builder must first verify this signal is discriminating, that
  the owner pins at the request and not at the handshake. If it is not, fall
  back to a short sleep. A late cancel then only makes the test vacuous. It
  cannot fail it.
- Cancel, then assert exactly what is asserted today (not nil, not `ErrBadConn`,
  `context.Canceled`).
- Release the write lock, close the dedicated conn, `waitOwnerConns` back to
  baseline, and assert the count is at most 1.
- **Spike required before committing to this:** confirm a blocked INSERT really
  waits on the busy handler through the owner's pinned conn. Run it once with
  the lock held and see the exec not return for several seconds. If Turso
  returns busy at once instead, abandon the lock design and keep the CTE but size
  it with the sibling test's 2,000,000-row `count(*)` form. Say which was used.

**Mutation:** in `wire/client/session.go` make a cancel return
`driver.ErrBadConn`. The test must fail on the `ErrBadConn` assertion. Name the
test. Run it under `RELEVO_DBTEST_OWNER=1` too, because the failures were in
the owner-mode job.

## 5. `TestDrainOutboxIsOneTransaction` (`sync_exchange_test.go:~475-560`)

**Pins today:** `DB.DrainOutbox` reads the outbox entries and the rows they
name in one transaction, so the single pooled connection is never returned
between the two reads. A split wrapper lets a queued waiter in, and the drain
then waits out the waiter's 5 s hold. The assertion is `drain duration <
waiterHold`.

**Cause:** the assertion is the drain's own speed. The comment itself notes a
1000-entry drain takes over 2 s on macOS runners; under load it reaches 5 s.

**Rewrite (observe the guarantee, not its speed):**
- The waiter does a write instead of holding. Its body runs
  `UPDATE repo SET origin_url = '<marker>' WHERE id = 'r0'` and returns at once.
  There is no `waiterHold`, no `stop`, and no `time.After`.
- Order the waiter without a sleep. Start the drain goroutine, then
  `pollUntil` `d.sqlDB.Stats().InUse >= 1` (the drain has the pool's one
  connection), then start the waiter. It queues on the pool.
- After the drain returns and the waiter is joined, assert that every drained
  entry for `r0` carries the row state that existed *before* the drain, and not
  the waiter's marker.
  - One transaction: the waiter cannot run until the drain returns, so the rows
    show the pre-drain value.
  - Split: the waiter takes the connection between the two transactions and
    commits, so the second read sees the marker and the assertion fails.
- Three attempts stay. The marker value differs per attempt, and the expected
  value is whatever `r0` held before that attempt's drain (first `"u999"` from
  `seedDrainBacklog`, then the previous marker). Use `findDrained`/
  `exchangeColumn` from the same file.
- Remove `waiterHold`, `drainWhilePoolHeld`'s timing, and the `time` import if
  nothing else in the file needs it (it does: the rival helpers). Check the
  imports.
- The file is already over 600 lines (it is on the size allow list). The rewrite
  must not grow it. If it does, say so; do not add an exclusion.

**Known weakness to measure, not assume:** if the waiter queues after the
drain's first transaction already ended, a split drain passes (a false pass,
never a false failure). The mutation run below decides whether this is
acceptable. If the split mutant is not caught 50/50, add a second sync: poll
`Stats().WaitCount` increasing before the drain is allowed to proceed. That
needs the drain to start only after the waiter is queued behind a connection
the test holds, so set it up that way: the test holds the one connection, starts
the drain (queues), polls `WaitCount==1`, starts the waiter (queues), polls
`WaitCount==2`, releases. Pool wake-up is random among waiters (`TakeRandom` in
Go's `database/sql`), so use this form only if the waiter is made unable to win
the race, for example by having the waiter's write retried until the drain
returns. Prefer the simple form unless the mutant slips through.

**Mutation:** in `DB.DrainOutbox` (`sync_exchange.go:326`), split it into two
`d.Tx` calls (entries in one, rows in the other). `TestDrainOutboxIsOneTransaction`
must fail 50 of 50 runs. Name the test. Also run the old version against the
same mutant to confirm the new one catches at least as often.

## 6. Other wall-clock tests in the same class (include; cheap and clear-cut)

For each, what it pins and the rewrite:

1. `db_test.go:~108`, `Open` while another connection holds the write lock: the
   `elapsed < 2s` assertion.
   - **Pins:** a current-schema `Open` does not need the write lock.
   - **Why it is redundant:** the holder never releases and `busyTimeoutMS` is
     200, so an `Open` that needed the lock would return an error, which the
     preceding `err != nil` check already fails.
   - **Rewrite:** delete the elapsed assertion and the `time` use.
   - **Mutation:** make the schema check take the write lock; the test must fail
     on the `Open` error.
2. `db_test.go:~520` `TestOpenWithShortBusyFailsFast`: `elapsed < 2s`.
   - **Pins:** `Options.BeginRetry` bounds a busy `Tx`, overriding the global
     default.
   - **Rewrite:** set the global `beginRetryFor` to 60 s in the test, with
     restore in `Cleanup`, so an ignored option waits 60 s. Assert `elapsed <
     30 s`. The real work is milliseconds, so the margin is generous, and the
     mutant is still caught.
   - **Mutation:** ignore `o.BeginRetry` in `db.go:~161-165`; the test must fail
     on the bound.
3. `openlock_test.go:~108` `TestReadOnlyOpenTriesOnceForTheLock`: `elapsed <
   1s` against `shrinkOpenLockWait(2s)`.
   - **Pins:** a read-only open tries the lock once and does not poll.
   - **Rewrite:** raise `shrinkOpenLockWait` to 30 s and the bound to 10 s.
   - **Mutation:** make the read-only open poll; it waits 30 s and fails the
     bound.
4. `openlock_test.go:~249` `TestTwoSpellingsOfOnePathShareTheLock`:
   `elapsed > 1s`.
   - **Pins:** a second spelling of the path shares the lock instead of
     flock-ing against this process.
   - **Why it is redundant:** `shrinkOpenLockWait(3s)` means a failure returns
     `ErrLocked`, which the preceding `err` checks already catch, plus
     `handleCount == 3`.
   - **Rewrite:** delete the elapsed assertion.
   - **Mutation:** use the uncanonicalised path as the map key; the test must
     fail on the `openDirect` error or on `handleCount`.
5. `openlock_test.go:~184` `TestAWaitingOpenDoesNotBlockAnotherPath`:
   `time.Sleep(100ms)` to let the waiter reach the lock, with a 5 s wait.
   - **Pins:** a waiting open does not hold a process-wide lock that blocks an
     open on another path.
   - **Rewrite:** replace the sleep with `pollUntil` on the waiter's `directHandles`
     entry existing (`directHandles.paths[canonicalPath(held)] != nil`, under
     its mutex). Raise `shrinkOpenLockWait` to 20 s so a loaded second open
     cannot outlast the wait.
   - **Mutation:** hold `directHandles` across the lock wait in
     `acquireHandle`; the test must fail on `openDirect(other)` blocking and the
     waiter ending first.
6. Fail-direction-only timeouts to delete: `close_test.go:~75`
   (`time.After(5s)` on `pc.started`) and `query_owner_test.go:~114`
   (`time.After(2s)`). Both become plain channel receives. The `cancel()` in the
   second must stay reachable on failure, so wrap it with a `t.Cleanup(cancel)`.
   `cancel_modernc_test.go:~39` (5 s) is the same class and gets the same
   treatment.

## Left alone, with reasons (list these in the report)

- `cancel_turso_test.go:55,66,133,141`, `cancel_modernc_test.go:28`: the 150 ms
  sleeps before cancel and the 1 s "returned within the grace" bounds. The bound
  is the property (the client must not wait for the engine), and the grace is
  250 ms. These have no CI failures in the evidence. Widening the bound would
  make the property vacuous on a fast engine. If they start failing, they need
  an owner-side hook, which is its own change.
- `db_test.go:~419` `TestTxRetriesABusyBegin`: the holder sleeps 300 ms against
  a 3 s window. Slow only makes the retry longer, never fails.
- `TestTxGivesUpOnABusyBeginAfterTheDeadline`: the holder is released by a
  channel, so it is already deterministic.
- `poolbound_test.go:~102` (300 ms context deadline) and the goroutine-count
  slack: the deadline *is* the property and fires regardless of load.
- `reexec_reap_test.go:~107` `time.Sleep(500ms)`: it waits to see that nothing
  *more* happens, which cannot be a sync point. A false pass at worst.
- `ulid_test.go:~32` `time.Sleep(2ms)`: the sleep guarantees a later
  millisecond; a longer one on a loaded machine cannot break the order.
- `openlock_test.go:~130` `elapsed < wait`: a lower bound.
- `internal/db/wire/...` sub-packages: out of scope for this round.
