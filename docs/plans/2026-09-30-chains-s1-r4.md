# Chains slice 1 · round 4 — the `chain` verb: start (members, plan copies, plan 1)

One-shot builder round. It starts from a branch where rounds 1, 2 (migration 016, the chain tables)
and 3 (`policy.chain`) are merged, and runs in parallel with round 8 (status surfaces) on another
builder; the MasterMind merges the two afterwards, and the slice lands as one PR. Commit, never amend.
Ends with `make check` green.

## Deliverable

`relevo chain` starts a local chain: it validates everything before anything exists, cuts the builder's
worktree, creates the builder + reviewer + planner (and, when the security phase is on, security)
members plus the chain row atomically, copies the plan files, and sends plan 1 to the builder. Also
fixes the local `bind --worktree --base` cut, which the design assumes and the code does not do today.
`--resume` is round 6; `--server` is slice 3 and is not added.

## Exact shapes

```go
// internal/relevo/chain_start.go
type ChainOptions struct {
    Name string
    Plans []string // ordered source paths; at least one
    Feature string; NoFeature bool; Ticket string
    Base string
    MaxCorrections *int
    ReviewerActor, PlannerActor, SecurityActor string
    Security *bool
    MasterMindID string
}
type ChainResult struct {
    Chain   db.ChainRow
    Members []store.Binding // builder, reviewer, planner, [security]
    Plans   int
}
func ChainStart(ctx context.Context, rt Runtime, opts ChainOptions) (ChainResult, error)
```

Pinned behaviour:

- Validation, all before anything is created: `store.ValidName(name)`, `len(name) <= 27` (the longest
  member suffix is `-plan`; names are never truncated); exactly one of `--feature`/`--no-feature`
  (`RequireFeatureChoice(feature, noFeature, false)`, bind.go:172); `store.ValidFeature`/`ParseTicket`;
  at least one plan, each readable and non-empty after `bytes.TrimSpace`; each member name
  `<n>`, `<n>-rev`, `<n>-plan`, `<n>-sec` (security only) passes `ValidName` and is free of both a
  binding record (`rt.Store.Load` = `store.ErrNotFound`) and a chain row; the actor shapes via
  `actorShape` (writer_role.go:46): builder a writer, the other three readers; each actor resolves via
  `resolveRole` (candidate.go:226); the caller's mastermind resolves (`resolveVerbMasterMind`).
- The builder is cut from `--base` (else HEAD) exactly as `bind --worktree` cuts: branch
  `relevo/<n>`, worktree `rt.Store.WorktreePath(<n>)`, `rt.Git.AddWorktree`.
- Members: the builder binding mirrors `Add`'s literal (add.go:391-420: CWD, Worktree, Branch, Base,
  BaseRef, Repo, Role `builder`, Shape writer); each reader binding carries CWD = the builder's
  worktree, its actor name as Role, Shape reader, no worktree, no gate. All members carry the
  mastermind id, feature and ticket.
- Plans are copied into `rt.Store.ChainDir(name)` as `plan-1.md`... and the chain row stores those
  paths; a later edit of the source changes nothing.
- `Tx.CreateChain` writes the chain row and every member in one transaction (round 2); the initial
  state is status running, phase build, step building, plan 1, corrections 0, awaiting (builder, 1);
  settings are the resolved values (§5) and the member names are the four part columns.
- Plan 1 is handed over with the ordinary `Send(ctx, rt, <n>, ChainPlanPath(name, 1), SendOptions{})`
  after creation: the member already carries its resolved candidate. (5a moves this handover to
  `sendChainRound`, so the send refusal 5a adds never bites a chain's own start, and pins the started
  chain's plan 1 with a test.) A failed first send leaves the chain row running and the builder member
  NEEDS YOU; round 5b's sweep turns that into a chain halt.
- `--json` prints `ChainDoc` (name, members with parts, plans, status, phase).

The `--base` fix (design §6.1 says the builder is cut from `--base` as `bind --worktree` does; the
code today computes `base` from `HeadCommit` only, add.go:310-337, and `--base` reaches the local cut
nowhere but is accepted): in the local cut, when `opts.Base != ""` resolve it with
`rt.Git.RefSHA(ctx, opts.Repo, opts.Base)` (refs.go:137) and refuse `base %q not found` when it does
not resolve; keep `HeadCommit` for the default. Both `bind --worktree --base` and the chain get the
same behaviour. Update the `--base` flag help text in `cmd/relevo/bind.go:134` to drop "with
--server"; the registry flag list does not change.

- If `internal/relevo/add.go`'s local cut cannot be given `opts.Base` without touching the `--branch`
  and `--cwd` arms (add.go:245-309), halt and report; do not build a second worktree cutter.
- If `internal/relevo/bind.go`'s `create`/`Add` cannot be reused for candidate resolution without
  taking `rt.Store.WithLock` (they each take it, bind.go:702, add.go:422), halt and report your reuse
  plan (extract a lock-free helper) instead of copying their preflights wholesale.
- If `rt.Git`'s interface has no `RefSHA` reachable from `internal/relevo` (refs.go:137), halt: the
  `--base` premise cannot be honoured as written.
- If `.chains` collides with a state-root walker (`internal/relevo/gc.go`, `store.PruneWorktreeDirs`,
  the seal walk), halt and report which one.
