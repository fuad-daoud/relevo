# Chains slice 1 · round 8 — `status` and the statusline show one chain row

One-shot builder round. It starts from a branch where rounds 1, 2 (migration 016, the chain tables)
and 3 (`policy.chain`) are merged, and runs in parallel with round 4 (the `chain` verb) on another
builder; rounds 4-7 are NOT on this branch. Build the surfaces from the chain rows alone
(`Store.Chains`, `db.ChainRow`); build test fixtures by writing chain rows and member bindings
directly (`Tx.CreateChain`), never through `ChainStart`, `chainApply` or `relevo chain`, which do not
exist here. `cmd/relevo/status.go`'s chain branch resolves the name through `Store.Chain` only. The
MasterMind merges this branch with the others; the slice lands as one PR. Commit, never amend. Ends
with `make check` green.

## Deliverable

`relevo status` shows one row per chain (status, phase, step, plan i/N, corrections, the active
member) in place of its members' rows; `relevo status <chain>` lists the members under it; the
statusline renders one entry per chain, `chain x · plan 2/4 · reviewing · 1 correction`, with NEEDS
YOU on a halted chain. A DONE chain's members keep their ordinary rows.

## Exact shapes

```go
// internal/view/chain.go
type ChainFacts struct {
    Status string `json:"status"`   // running | halted | stopped | done
    Phase string  `json:"phase"`
    Step string   `json:"step"`
    Plan int      `json:"plan"`
    Plans int     `json:"plans"`
    Corrections int `json:"corrections"`
    Awaiting string `json:"awaiting,omitempty"` // the active member
    Reason string `json:"reason,omitempty"`
}
func ChainSegment(f ChainFacts) string // "plan 2/4 · reviewing · 1 correction"
func ChainDisplay(f ChainFacts) string // running -> ACTIVE, halted/stopped -> NEEDS YOU, done -> DONE

// internal/relevo/chain_status.go
func applyChains(rep view.Report, chains []db.ChainRow) view.Report
func ChainStatus(ctx context.Context, rt Runtime, name string) (view.Report, error)
```

Pinned behaviour:

- Member rows are removed while their chain exists and is not `done`; the chain row takes their place.
  `ChainStatus` (single name) always lists the members underneath, builder first.
- The synthetic row carries `Name` = chain name, the owner/mastermind fields so the existing
  mastermind filter and sort work, `Display` from `ChainDisplay`, `Chain` facts, and `Detail` =
  the halt reason for a halted chain.
- Statusline: the row's status column follows the chain (NEEDS YOU for halted or stopped, otherwise
  ACTIVE/phase text), and the middle segment is `ChainSegment` — the spec's example
  `chain x · plan 2/4 · reviewing · 1 correction`; `--line --json` adds the `chain` field.
- Human `relevo status` prints the chain row as
  `x  <cwd or ->  chain  <status>  plan i/N · <step> · k correction(s)` plus the reason line; members
  follow in the `status <chain>` view.
- `status --all` applies the same replacement; `done` chains leave members visible (they are done and
  hidden by the normal rules).
