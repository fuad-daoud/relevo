# Plan: SD-1239 - Batch Import Order & Per-Entry Refusal (Sync Rebind & Drop Repair)

## Verified Facts

- `Exporter.entries` (`internal/synclog/export.go:166`) builds `upserts` then `deletes`, then appends upserts first, deletes after. `sortParentsFirst` / `sortChildrenFirst` (`export.go:281, 291`) order by table position in `db.SharedTables` (`internal/db/shared_tables.go:22`) only; within a table the order is commit order.
- `applyBatch` (`import.go ~330`) calls `fetchAndApply` -> `applyEntries` (`import.go ~395`). One `db.Tx` holds all entries; the first `applyEntry` error aborts the tx. `refused(err)` (`db.ErrInvalid` or `ErrInvalid`) makes `applyBatch` build one `Drop` for the whole batch and call `past()` to move the mark.
- The snapshot path already does the finer thing: `writeChunk` (`snapshot_chunk.go:63`) records an FK/UNIQUE failure (`db.ErrInvalid`) as a deferred entry and keeps the tx open ("a statement a foreign key refuses fails alone and leaves the transaction open, which the engine's tests pin"); `ErrInvalid` (not-owner, unreadable body) rolls the chunk back and `applyChunk` re-writes it without that entry; `applyUntilDone` / `applyPass` (`snapshot.go:249, 280`) retry deferred entries up to `maxSnapshotPasses` and stop when a pass applies nothing. Reuse this machinery for the batch path.
- Every UNIQUE index on a shared table is origin-scoped or reached through an origin-owned parent: `binding_record(origin, owner, name) WHERE archived_at IS NULL`, `binding(origin, name, created_at)`, `repo(origin, ...)`, `mastermind(origin, harness_kind, session_id)`, `chains(origin, owner, name)`, and `round(binding_id, number)`, `event(binding_id, seq)`, `artifact(round_id, kind, consult_id)`, `transcript(owner_kind, owner_id, seq)` (`db/migrations` 001, 014, 016). `ExchangeUpsert` stamps the owner column from the resolved origin (`ownedValues`, `db/sync_import.go:180`). So a UNIQUE conflict on import is always against a row of the SAME origin. No entry ever needs to touch another origin's row.
- Foreign keys among shared tables (migrations 001/003/004/016): `binding.repo_id->repo`, `binding.forked_from_binding_id->binding` (self-reference), `round.binding_id->binding`, `event.binding_id/round_id`, `artifact.round_id->round`, no cascade; `binding_event` and `round_file` -> `binding_record` ON DELETE CASCADE; `chain_event` -> `chains` ON DELETE CASCADE; `chain_member`, `chain_check` declare no FK. (`planner` is not a shared table.)
- Drops are stored cumulatively as strings in kv `sync.trouble` (`sync.Trouble.Dropped`, `internal/sync/sync.go:102`, `TroubleFrom` `steady.go:278`, shown by `relevo db sync status`); only `relevo db sync retry` clears them (`ClearDroppedTrouble`). `SetImportMark` is forward-only (`db/sync_exchange.go:66`), so a mark cannot be rewound today.
- The log still holds the dropped batches (a drop moves the mark, it does not delete log entries) unless compaction passed them; below a floor the snapshot path takes over.

## 1. Export: Deletes Before Upserts

Behaviour: in `Exporter.entries`, emit the batch's delete entries first (children-first as now), then its upserts (parents-first as now). Nothing else about the batch (coalesce, owned, pendingParents, blob rewriting, `pending` list) changes. Wire format and ProtocolVersion do not change; only entry order inside one batch.

FK safety review (confirmed against the schema):
- An upserted row (including parents pulled by `pendingParents`, which are only pulled when the row exists) is present at drain time, so its parents exist on the origin and are not in `deletes`. A delete can therefore never remove a parent that an upserted row's NEW state needs.
- Deleting a `binding_record` / `chains` row cascades to its events/files/chain_events on the importer; the origin cannot hold an upsert of those children (their parent is gone), so nothing is lost that was going to be sent. Cascaded orphans are already skipped by `owned()`.
- NOT safe in one narrow case (explicitly named here and in commit message): a row that is re-pointed away from a parent which is deleted in the same window (`binding.repo_id`, `binding.forked_from_binding_id`, `event.round_id`). The importer still holds the child pointing at the old parent until the child's upsert, which now comes second, so the parent's delete is refused by the FK. A fixed importer defers and retries that delete (section 2). A v0.18.0 importer drops the whole batch for it, where the old order applied it. Accepted: the case needs a re-point and a delete of the same parent in one export window, is rarer than the name reuse bug, and heals with the fleet upgrade; the repair replay (section 4) re-reads any batch it hit.
- Self-reference (forked binding): two deletes in one table are not ordered by parentage (stable sort by table only). Same resolution: deferral on the fixed importer. Do not add a within-table sort.

## 2. Import Policy (ONE): Apply Per Entry, Refuse Only the Failing Entry

Recommendation: (b). Why not (a): deleting a same-origin conflicting row cascades its children (`binding_event`, `round_file`, `chain_event`) which are never re-sent, so (a) would trade a dropped batch for silently lost history; it also treats a bad row as stale on a guess. Why not (c): holding the origin stalls every later row of the machine for one entry and has no way to release without an owner. (b) needs no guess: an old-order batch resolves itself because the delete that frees the key is later in the same batch.

Behaviour of the batch path (`applyEntries` / `applyBatch`), for the entries of one batch inside the one transaction that also moves the mark:
1. Apply entries in batch order. An entry that fails with `db.ErrInvalid` (UNIQUE, FK) is set aside, not fatal; the tx stays open.
2. After the sweep, retry the set-aside entries in passes while a pass applies at least one entry (bounded by the existing `maxSnapshotPasses` / `i.passes`). An old-order upsert whose key is freed by a later delete applies on pass 2; a delete refused by a child that a later upsert re-points applies on pass 2.
3. An entry that fails with `ErrInvalid` (errNotOwner, unreadable body, not a shared table) is refused immediately: roll the batch tx back, record a per-entry `Drop{Origin, Seq: entry.Seq, Reason}`, and re-apply the batch without that entry (same loop as `applyChunk`), so entries before it are not lost with it and a row that landed under the wrong owner is never kept. Ownership is unchanged: `owns` / `ownsAfterWrite` / `errNotOwner` still run for every entry, and nothing in this policy deletes or rewrites a row another installation owns (it deletes nothing that the origin did not say).
4. Entries still failing when passes stop (no progress) are refused individually: each becomes its own `Drop` with the failing entry's sequence and its error text, and the mark still moves to the batch tail in the same tx. All other entries of the batch stay applied. A swap (two rows of one origin exchanging a unique value in one window) is exactly this case: each upsert is blocked by the other's old value, no pass progresses, both entries are refused visibly and the rest of the batch applies. Ordering cannot fix it, and breaking it by deleting the blocker would cascade-delete history (rejected). The rows stay at their pre-swap values on the reader until both are next written; that residue is the documented limit, and it is visible.
5. Visibility: per-entry drops go through the existing `ImportResult.Dropped` -> `TroubleFrom` -> `sync.trouble` -> `relevo db sync status`. `Drop.String()` already names origin, sequence and reason; the reason names table and pk (via `applyEntry` error text). Batch-level drops remain for what is truly batch-wide (verification, unreadable doc entries, missing blobs). `Moved()` stays true when entries applied or any drop recorded.
6. Keep `applyEntries` under 70 lines by extracting the sweep and pass into helpers shared with `writeChunk` (`internal/synclog/importentry.go`). Keep `import.go` under 600 lines.

Mixed fleet (no protocol bump, wire shape unchanged):
- v0.18.0 exporter -> fixed importer: old-order batches apply via deferral. Fixed.
- fixed exporter -> v0.18.0 importer: delete-first batches apply cleanly; only the re-point-then-delete-parent case of section 1 still drops a batch on the old importer.
- fixed <-> fixed: both paths.
Entries already dropped by v0.18.0/v0.17.3 importers heal only via section 4 on that machine.

## 3. Children of a Parent Lost Earlier

With per-entry apply a batch that carries an unrelated refused entry no longer takes the parent rows down with it, so no new cascade is created. For children already orphaned by past drops:
- A child that fails the FK after all passes is refused as its own `Drop` (visible, never silent) and does not take other entries with it. It is not retried forever on its own: the parent's entry is in the log at an earlier sequence, so recovery is a replay of the log from before the lost parent, which section 4 does once, automatically, and which any later FK refusal can request by the same rewind.
- Expose the rewind as a small function in `internal/sync` (`RewindImport`) used by section 4; do not wire a second trigger in this change.
- The exporter does not need to re-send parents: `Reconciler` compares the file to log head hashes, and head still holds the lost rows, so reconcile would send nothing. Do not rely on it.

## 4. Repair of Existing Damage (zen, contabo)

Mechanism: the log still holds the dropped batches, so a fixed importer only needs its mark for the laptop origin put back before the first dropped batch. One-time automatic pass:
1. db: add `(*DB).RewindImportMark(origin string, seq int)` (`internal/db/sync_exchange.go`) that sets a mark DOWN, explicitly named so the forward-only guard of `SetImportMark` stays intact for every other caller.
2. internal/sync (`internal/sync/replay.go`): a pass run once at the head of the steady import before `imp.Import()` (`steady.go ~255-265`, in the same closure that has the local kv). It is keyed by a kv marker `sync.replay.refused` (value = generation string "1") so it runs once per machine, and only after the fixed binary runs. For each remote origin named in the cumulative `sync.trouble` `Dropped` lines ("dropped entries from <origin> up to sequence N: ..."), take the smallest N, and compute raw target `max(0, Nmin - 4*DefaultBatchSize)` (per MasterMind C1). When dropped lines for an origin fill the cap `maxDroppedReports` (50), rewind that origin to 0 (per MasterMind C2).
   Batch boundary rule: `replayed()` skips any entry whose batch began at or before the mark (`e.Batch <= mark`), so a rewind mark landing in the middle of a batch skips the rest of that batch, causing `firstHole` to report a Gap and hold the origin. To ensure the mark lands cleanly on a batch boundary, the rewind pass resolves a boundary from the log before setting the mark: it reads entries past the raw target through the transport (`PullRange`), takes the first entry with `Seq > target`, and sets the mark to `entries[0].Batch - 1` (the start of that batch minus one, which is `<= target`). This lookup applies only at or above the origin's compaction floor. Below the floor the log keeps only each row's newest entry, so the entry after the target may be gone; there the mark is set to the target itself, and the snapshot path, which needs no batch boundary, replays the region up to the floor. The marker carries a generation, and a machine holding an older one runs the pass again.
   Then write the marker. Parse the sentence with `ParseDrop` placed next to `Drop.String()` in synclog.
3. Replay is safe: re-applying entries in log order from a lower mark ends in the same final state (upserts idempotent, delete of an absent row a no-op, owner rule unchanged); entries before the first drop are not re-read. Where the log was compacted past the rewound mark, the existing snapshot path (`snapshots`) takes over.
4. If the owner already ran `relevo db sync retry`, the dropped lines are gone and the pass finds nothing; in that case the owner runs the escape hatch in 5. Do not clear dropped lines inside the pass (the status keeps them until the owner's retry); the replay itself adds none once it works.
5. Escape hatch with no SQL: `relevo db sync replay <origin-or-label> [--from <seq>]` is NOT added in this change (no new verb); deleting the kv marker is unnecessary: the owner runs `relevo db sync retry` only after status shows no new drops. If the laptop's drops were already cleared, file a follow-up for a verb rather than hand SQL.
What the owner runs: upgrade zen and contabo to the fixed release; the daemon's next import replays the laptop origin and applies the missing 4 bindings, 4 chain_member rows, 14 rounds, and the stale `01M519FJ...` binding_record is removed by the replayed delete (its delete entry sits in the dropped batch's tail). Then `relevo db sync status` on each, then `relevo db sync retry` to clear the old lines. The laptop needs no action. Verify by comparing the damage table counts (binding 1450, chain_member 346, binding_record 1318) with `relevo db query`.

## MasterMind Corrections Implemented

- C1: Replay start rewinds each origin to `max(0, Nmin - 4*DefaultBatchSize)`. DrainOutbox prepends pending parents on top of the 256-entry window, so batches can exceed 256. Overshooting is harmless due to idempotent replay.
- C2: When an origin's dropped lines reach `maxDroppedReports` (50), rewind that origin to 0, allowing the existing floor/snapshot path to take over below the floor. Both cases tested: under cap uses Nmin math, at cap rewinds to 0.
- C3: Replayed entries pass verification. Tested replaying unsigned entries written before first signing, after origin has started signing, proving they apply cleanly without refusal or stalling origin.
- C4: Open-tx-after-UNIQUE-failure premise on Turso verified via `TestExchangeUpsertUniqueConstraintLeavesTxOpen` before implementation.
