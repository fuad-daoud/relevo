# Chains slice 2 · round 1 — the wire and the server carry a chain member's round

One-shot builder round. Starts from the branch as round 0 (main, `44463fd5`) leaves it; all rounds stack on `relevo/chains-s2` and land as one PR. Commit, never amend. Ends with `make check` green. Focused loop: `go test ./internal/serve/ ./internal/remote/... -run 'ChainMember|Gate|Verify' -count=1`.

### Deliverable

A server that can carry one chain member's round: a create may name an acceptance gate; the gate runs at each round's close; the binding view reports the closed round's gate result; a `gate` round-file route serves the log; a round form may switch verify off; `WhoAmI` advertises `chain_member`. The client marshals and sends all of it. No chain behaviour yet.

### Pinned behaviour

- The create's gate is stored verbatim on the server binding; a create with no gate stores "" and the binding behaves exactly as today (no check, no gate log).
- `gate_result` is the *closed* round's result and only that round's; a binding with no gate, an unclosed round or an older entry reports "". The client maps "" to `chain.GateNone` (round 3), never green.
- The `gate` file is served only for a closed round, like the other non-log kinds, and 404s when the log does not exist.
- `verify` absent leaves the server's own policy in charge; `verify=0` stores `RoundVerify=false` for that round and no verify consult starts at its close; `verify=1` stores true. A reader round stays verify-free regardless (`send.go:690`).
- The existing feature tokens keep their meaning; `chain_member` is additive and only this client's chain start reads it (round 2).
