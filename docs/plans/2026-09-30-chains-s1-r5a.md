# Chains slice 1 · round 5a — the daemon drives the chain: consumption, advance, trace, one delivery, send refusal

One-shot builder round. It starts from a branch where rounds 1-4 and 8 (status surfaces) are merged.
All later rounds stack on it and the slice lands as one PR. Commit, never amend. Ends with `make check`
green. This is the first half of the old round 5: after it a started chain runs itself through member
closes; the in-member repair before a red gate and the member sweep are 5b.

## Deliverable

Reconcile maps a member's round close to a `chain.Event`, calls `chain.Next`, performs the action
(seed the next member, halt, stop, finish) through the chain's own sender, and writes the chain state
+ trace row in one transaction. Member output is consumed (never delivered), exactly one end delivery
is queued when the chain ends, a manual `send` to a running chain's member is refused, the chain's own
plan 1 goes through the chain sender so the refusal never bites a chain's start, and every member
round runs with verify off (the reviewer replaces it). In this half a red gate goes straight to the
reviewer with event gate `red`; the repair round arrives with 5b.

## Pinned behaviour

- **`stopped`.** The new `queueReport` parameter is the caller's fact that this close is a stop: only
  `closeStopped` passes true, and it feeds the chain event kind `stopped`. `queueReport`'s existing
  `!b.StopRequestedAt.IsZero()` note and `stopped/graceful` entry keep today's behaviour, because
  `stop_test.go:199` pins exactly one `stopped/killed` entry per stop; do not make the parameter drive
  them.
- **Refusal.** A manual send (including `--dry-run`) to a member of a running chain fails with
  `ErrRunningChainMember` wrapped as `binding %q belongs to running chain %s; relevo stop %s first`,
  mapped to `conflict`; checked read-only in `sendPreflight`, again under `Send`'s lock and under
  `sendRemote`'s lock. Once the chain is halted or stopped, manual sends work again.
- **Verify off.** `sendChainRound` never requests verify: it sets the sent round's `RoundVerify` to
  false whatever `policy.verify.default` says. Every chain member round is verify-free; the reviewer
  replaces the verify consult.
- **Consumption.** A close whose binding is a member of a chain with status running records
  `consumed by chain <n>` in place of the MasterMind payload: same entry, `Confirmed: true`, appended
  with `tx.AppendLog`. `delivery.Queue` is not called (it forces `Confirmed=false`).
- **Event data.** Builder close: `Outcome` = the report entry's outcome, `Gate` = `green` when there
  is no gate record or `GateRecord.Result == "pass"`, else `red`. Reviewer close: `Verdict` from
  `chain.ParseVerdict(body)` on the in-memory body, before the reader output is stripped
  (reconcile.go:556-562 rewrites the file; a re-read there would find no block). Planner close:
  `PlanPresent` = the planner's output file (the `reportPathFor` path, stat'd with
  `rt.Store.StatFile`) exists and is non-empty. Security close: `Findings`/`FindingsGiven` from
  `chain.ParseFindings(body)`. A stopped close raises `stopped`.
- **Events.** `chainEventFromClose` maps (part, closing binding, body, outcome, gate, stopped) to
  `chain.Event`; `chainApply(ctx, rt, tx, b, ev)` loads the chain with `tx.ChainByMember`, ignores the
  close when `Next`'s `(Member, Round)` does not match `Awaiting`, and otherwise calls `Next` and
  performs the action. `needs_you` events arrive with 5b's sweep.
- **Actions.** `send` → `sendChainRound` to the target member (the seed text from round 1's
  `chain.Seed` with a `chain.SeedView` built from the chain row, the plan copies and the members'
  artifacts); `halt`/`stop`/`finish` → `chainTerminal`. The event, the new state and the trace row are
  written with `Tx.ChainSaveWithEvent`; the action's send is recorded on the member's own binding+log
  in the same critical section. If the send fails, the chain halts in the same critical section with
  `member <name> could not start: <err>` and the member keeps the NEEDS YOU `startRound` left
  (`sendChainRound` sets it, as `Send` does at send.go:565-581). `Awaiting.Round` is filled from the
  binding `sendChainRound` returns and is never 0.
- **`sendChainRound(ctx, rt, tx, b store.Binding, text string) (store.Binding, error)`** is `Send`'s
  in-lock core as a reusable helper: reload the member under the tx, refuse an open round/pending
  marker/live PID, stage `text` at `rt.Store.PromptPath`, `capture.Baseline`, create the reader
  scratch when the member is a reader (`CreateScratchFrom`), `composePrompt`, `repickStale`
  (repair.go:125 pattern), `startRound`, then set `RoundBaselineTree/Head`, clear `RoundClosedTree`,
  `RoundStartedAt`, `FinishPending`, `State = active`, `RoundVerify = false`, append the prompt entry
  (`KindPrompt`, note naming the chain step) and save with `Tx.SaveWithLog`. A `startRound` failure
  leaves the member NEEDS YOU exactly as `Send` does; the error is returned wrapped with the member's
  name.
- **One end delivery** (§9.2). `chainTerminal` writes the status/reason and the trace row, then
  `delivery.Queue` one entry on the builder member: `Direction: DirToMasterMind`, `Kind: KindChain`,
  `Round` = the builder's current round, payload carrying status, phase, plan i/N, total corrections,
  findings, on halt the reason and `relevo chain --resume --name <n>`, the builder branch, and
  `relevo show <n> --trace`. Findings come from the trace's `security_closed` event (the chain row has
  no findings column); a chain that never ran security carries 0. The terminal transition happens
  once, so the payload exists once; a second tick cannot add another.
- **Trace.** One `chain_event` row per transition: `phase`/`step` before the event, the closing member
  and its round, `Event`/`Action` encoded with round 1's `Encode`, the halt reason when there is one;
  `Tx.ChainEventAppend` allocates the seq (round 2). A close that did not advance the chain writes no
  trace row.
- **Plan 1.** `ChainStart` hands plan 1 over with `sendChainRound`: the member carries its resolved
  candidate already, so nothing of `Send`'s preflight is needed; a failure leaves the chain row
  running and the builder member NEEDS YOU (5b's sweep turns that into a halt).

## Mutation checks (design §12)

- Make `changes` advance to the next plan → `TestChainReviewerChangesSeedsCorrection` fails.
- Make `awaiting` match any round → `TestChainIgnoresACloseForAnotherRound` fails.
- Count a missing verdict as a pass → `TestChainReviewerCloseWithoutAVerdictHalts` fails.
- Double-queue the end payload (drop the terminal guard) → `TestChainFinishQueuesExactlyOneDelivery`
  fails.

## Halt conditions

- If `queueReport` is not the single funnel every close path reaches (today: `closeOnMarker` twice,
  the unmarked exit, `closeStopped`, remote catch-up), halt and report the path that bypasses it
  before adding a second hook.
- If `Tx.ChainSaveWithEvent` (round 2) cannot write state + trace in one db transaction, halt.
- If starting a member's round requires more of `Send`'s preflight than `sendChainRound` carries
  (candidate resolution, availability gating), halt and report; do not copy `sendPreflight`.
- If `ChainStart` cannot hand plan 1 over through `sendChainRound` after `Tx.CreateChain` (it takes a
  fresh `rt.Store.WithLock`; re-entering the create's own lock would deadlock), halt and report the
  call site; do not keep the ordinary `Send` with a refusal that bites the chain's own start.
