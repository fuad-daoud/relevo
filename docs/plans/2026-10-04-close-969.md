## #7: the unreachable halt never clears

**What happens now:**
- A server unreachable past `roundBudget(b)+unreachableGrace` triggers a halt
  that sets `State = StateNeedsYou` and stamps `Halt`, `HaltAt` and
  `HaltNotifiedRound`.
- When the server answers again, the apply clears only
  `RemoteUnreachableSince`. Neither the running arm nor the queued arm touches
  `State` or `Halt`.
- So `WaitOutcome` answers needs-you on every call until the server closes the
  round, even though the round is visibly running.

**Decision: fix it.** The only reason for this halt was "we can't see the
server". Once the server answers Running or Queued, that reason is gone.

**Behaviour:**
- On a Running or Queued view, a binding that is NEEDS YOU *because of the
  unreachable halt* goes back to `StateActive`.
- Clear `Halt` and `HaltAt`, and set `HaltNotifiedRound` to 0. If the server
  drops out again, that is a new episode and its halt must queue its own entry.
- Leave every other halt alone: a server `view.Halt`, a 404, an auth halt, or a
  local halt.
- Add no new log entry kind. Write one `slog.Info` line when the halt clears.

**Where the code goes:**
- `remote_sync.go` was 599 lines against a 600-line limit and is not in
  `scripts/check-filesize.allow`, so the code goes in
  `internal/relevo/remote_unreachable.go`: the halt-text builder, a predicate
  that recognises that text on `b.Halt`, and the clear function.
- The unreachable branch of `applyRemoteErr` moves into that file as well. With
  the builder and the clear in place the file still did not fit under 600, and
  the plan's own instruction for that case is to move the whole unreachable
  branch rather than add an allow-list entry. All three pieces are one behaviour
  -- an episode the branch opens, the sentence it records, and the moment the
  server's answering ends it -- so they sit together.
- `remote_sync.go` keeps one call before `switch view.RoundState`, plus the
  three-line arm that hands the unreachable case to the new file. It ends at 589
  lines.

**Tests:** in `internal/relevo/remote_test.go`, next to the existing

## #8: the wait registration goes stale during a slow sync

**What happens now:**
- The wait registers once, then refreshes only after each pass.
- `delivery.WaitTTL` is 10s and a single remote request may take up to 30s, so
  one pass can outrun the whole TTL. `KVWaitClaims.Live` then reads the row as
  dead and deletes it, and the statusline escalates while a wait is running.
- Refreshing just before the sync is not enough, because one sync can run longer
  than 10s on its own.

**Fix: keep the registration fresh while the sync runs.**
- Around the sync call, re-stamp the registration on a ticker for as long as the
  sync runs.
- Tick at `delivery.WaitTTL/3`, and say where that number comes from.
- The ticker stops when the sync returns and is not started at all for an empty
  registration (`--peek`, or no wait store).
- Use the runtime clock, and keep writes best-effort, as `refresh` does.
- Do not change `WaitTTL`.
- The helper sits next to `waitRegistration`, so `Wait` does not grow.

**Test:** `internal/relevo/wait_liveness_test.go`, after
`TestWaitRefreshesWhilePolling`:
- `TestWaitKeepsRegistrationLiveDuringSlowSync`

**Mutation check:** remove the ticker start: the new test fails,
`TestWaitRefreshesWhilePolling` still passes.
