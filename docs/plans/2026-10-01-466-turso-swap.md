## The MasterMind's decision on the halt

`TestCancelInterruptsARunningStatement` fails under Turso because tursogo v0.8.1
cannot interrupt a running statement. The MasterMind checked the v0.8.1 sources:
`Connection::interrupt` and `set_query_timeout` exist only in Turso's Rust API
(`sdk-kit/src/rsapi.rs:1177-1188`, `core/connection.rs:4829`). They are not in the C
ABI (`sdk-kit/turso.h`), not registered by tursogo (`bindings_db.go` registers no
interrupt function), and there is no pragma for them. **Accept the gap. Do not add
an interrupt through purego, and do not upgrade tursogo.**

What must hold instead:

1. **The client never waits on a statement it cancelled.** Today a cancelled
   client blocks until the owner replies (the test waited the full 5 s). Under
   Turso the owner cannot reply until the statement ends, so the statusline's
   500 ms budget and every verb budget would stretch to the statement's length.
   In `internal/db/wire/client`, on context cancellation the client sends the
   cancel and then returns `ctx.Err()` at once, after a bounded grace for the
   owner's reply (a small named constant; say why in one comment). From then on
   that session is unusable: its next use reports `driver.ErrBadConn` through
   `IsValid`/`ResetSession`, so `database/sql` discards it.
   **Hazard:** never return `driver.ErrBadConn` from the cancelled call itself.
   `database/sql` retries a pool `Exec` on `ErrBadConn`, and that already produced a
   duplicate INSERT once in this code base (the #680 review). The cancelled call
   returns `ctx.Err()`; only the session's *next* use is refused.
2. **The owner lets the statement finish, then discards that connection.** It
   must not serve that connection again, and must not leak it. Check what a drain
   (re-exec) does while such a statement runs: the drain window is bounded, so
   confirm the exec is not held past it, and say so in the report with the lines.
3. **Tests.**
   - Move `TestCancelInterruptsARunningStatement` unchanged into a
     `//go:build modernc` test file: modernc still interrupts.
   - Add a Turso twin (`//go:build !modernc`),
     `TestCancelReturnsToTheClientWhileTheEngineFinishes`: a cancelled heavy
     statement over the wire returns `context.Canceled` to the client within 1 s;
     a new query through the same `*DB` then succeeds on a fresh connection; once
     the statement ends, the owner's live-connection count returns to its
     baseline. Size the heavy statement so it ends within a few seconds under

   - Add a both-tags test that the cancelled call is not retried: a cancelled

   - Mutations to run and report: remove the client's early return (the twin

4. **Docs.** In `docs/specs/2026-09-29-db-owner-design.md`, where cancellation is

### 1. Owner-mode: direct-only operations are an explicit, listed exception

and `engineCode` reads an engine's own error before it is put on the wire. A test
of a direct-only operation therefore opens a direct handle explicitly, in both
modes. That is a decided exception, not a bent test.

### 2. `TestOpenLeavesAnExistingFileAlone` is a product bug. Fix the product, not the test.

Under modernc, closing the last connection checkpoints the WAL. Under Turso, the
owner's handle leaves the marker in a 531 KB `-wal`. Find why the owner-side close
does not checkpoint the way a direct handle's `Close` does (your round-1
deviation #2), and make the owner's direct handle checkpoint on close exactly
like any direct handle. The test stays unchanged and must pass in both modes.
A daemon that stops without checkpointing leaves the next start a large WAL to
replay, and makes a file copy taken after shutdown incomplete.

### 3. Invalid UTF-8: repair on write in both engines; repair once on conversion

Your probe showed that Turso refuses to write invalid UTF-8 and cannot read it.
relevo stores harness output, which can hold invalid bytes.

  place in `internal/db`: the connector wrapper's `NamedValueChecker`, or the
  single place where arguments are bound. Do it under modernc too, so a file
  written after a downgrade stays readable by Turso. `[]byte` arguments are
  untouched: compressed columns are BLOBs.
- **On conversion:** add `repairInvalidText(conn)`, driver-neutral, run under
  modernc. For every table and every column declared `TEXT` (read the schema from

## 1. The conversion never runs on a normal upgrade (must fix)

`convertLegacy` (`internal/db/convert.go`) runs only when `<path>-shm` exists.
SQLite deletes its `-shm` on a clean last close, and the normal upgrade path is a
clean close: the old daemon drains, `DB.Close`s `relevo.db`, then re-execs onto
the new binary. On that path the conversion is skipped entirely:

- no `.pre-turso` backup, which #466 requires before the switch;
- no `repairInvalidText`, so any invalid UTF-8 already in the file reads as
  "database is corrupt" under Turso.

The rehearsal test hides this: a copy of a live database always carries a
`-shm`.

**Fix: a durable marker inside the database records that the file was
converted.**
- Pick the marker and say why. Prefer something that lives in the file and
  survives `VACUUM INTO` and a plain copy, such as `PRAGMA application_id` set to a
  relevo constant. If you choose a row, it must be in a table `SCOPES.md`
  classifies as machine-local, never in a synced one. Check that nothing in relevo
  already uses `application_id`.
- **Trigger:** convert when the marker is absent, **or** when a `-shm` exists
  (that covers an unclean stop after a downgrade). Reading the marker before
  Turso's first open needs modernc; a raw read of the header field from the file
  is fine too if you choose `application_id`, and avoids opening a pool on every
  start. Say which.
- **Order:** backup (skipped if `.pre-turso` exists), checkpoint (TRUNCATE, not
  busy), `repairInvalidText`, **then set the marker in the same transaction as the
  repair, or right after it**, close, sidecar check. A kill before the marker is set
  re-runs the conversion; a kill after it leaves a converted file. Prove both with
  the existing step hook.
- A fresh database that the Turso build creates gets the marker at creation, so it
  never converts.
- Tests (default build):
  - `TestConvertRunsOnACleanlyClosedLegacyFile`: a modernc-written file closed
    cleanly (no `-shm`, no marker), holding invalid UTF-8 text. Opening it makes
    the `.pre-turso` backup, repairs the text, sets the marker, and Turso then
    reads every row.
  - `TestConvertSkipsAMarkedFile`: no second backup, no second repair.
  - `TestFreshTursoFileIsMarked`.
  - Update `TestConvertSkipsAFileSQLiteClosedCleanly`: a clean but *unmarked* file
    now converts. Rename it to what it pins now, or delete it if
    `TestConvertSkipsAMarkedFile` replaces it, and say which.
- Mutations: drop the marker check from the trigger (back to `-shm` only), and
  `TestConvertRunsOnACleanlyClosedLegacyFile` fails; never set the marker, and
  `TestConvertSkipsAMarkedFile` fails.
- **Rehearsal:** `TestTursoConversionRehearsal` also runs the copy with its
  `-wal`/`-shm` *removed after a clean modernc close* (the upgrade path). It logs
  the repair counts for both.
- **Docs:** in `internal/db/migrations/README.md` or the persistence spec, one
  paragraph: the marker; that running a pre-Turso relevo on a converted file and
  then upgrading again does not re-run the repair (an older build writes no

## 2. The open-lock wait holds the process-wide mutex

`acquireHandle` (`internal/db/handles.go`) holds `directHandles`' mutex while
`acquireOpenLock` polls for up to `openLockWait` (10 s). Every other direct open
or close in the process waits behind it, on any path. That includes `relevo
serve`, which opens one database per tenant.

**Fix:** never wait while holding the mutex. One way: check the map under the
lock; if the path is absent, release the mutex, acquire the flock, then re-take the
mutex and insert. If another goroutine inserted the path meanwhile, release the
flock you just took and join the existing entry. Any equivalent design is fine.
Test: `TestAWaitingOpenDoesNotBlockAnotherPath`. While one path's writable open is
waiting on a lock another process holds, a direct open of a second path in the
same process completes promptly.

## 3. Two spellings of one path deadlock the process against itself

`directHandles` is keyed by the raw path string, and `flock` treats two separate
opens of one file as independent locks even inside one process. So the same
`relevo.db` opened under two spellings (relative and absolute, or through a
symlink) makes the second open wait the full 10 s and then fail with `ErrLocked`.

**Fix:** key the map by the file's identity, not its spelling:
`filepath.Abs` plus `filepath.EvalSymlinks` on the database path (it exists by the
time the lock is taken), or the device and inode from `os.Stat`. Say which. Test:
`TestTwoSpellingsOfOnePathShareTheLock`, which opens through a symlink and through
a relative path while a handle is open; both succeed at once.

## Behaviour and its cases

**1a. Owner cleanup is bounded.** `(*conn).cleanup` must never let one uninterruptible
statement wedge a pin slot: keep the bounded wait for the request, attempt the
`ROLLBACK` best-effort under a timeout in a way that cannot hold the slot, then return
`<-c.s.sem`, discard the pinned connection and close the socket regardless. The slot
returns even while the statement still steps; the abandoned statement keeps running
until the engine finishes it, which is bounded by the engine's own work.

**1b. `db query` refuses `RECURSIVE` as a keyword.** A lexer-level scan (outside
strings, identifiers, and line/block comments, word-boundary, case-insensitive) refuses
any statement whose top level mentions `RECURSIVE`; `SELECT 'recursive'`, a quoted
identifier `"recursive"` and a comment containing it stay allowed. Refusal is a `usage`
error; the verb's usage/help/guide say it is a limit of the verb (the owner protocol
still runs any SQL — that is what 1a bounds).

**2. Deadline, row cap, honest conflict.** `db query` gets `--timeout` (default 10 s,
positive, at most `db.ReadOnlyHoldBudget`) and `--limit` (default 1000, ≥1). The
deadline covers dial, open and read; expired means a `refused` timeout error, no
fallback to a direct open. The row cap stops after `--limit` rows, and when a further
row exists it prints the rows that fit plus `truncated at N rows (raise --limit)` on
stderr (stdout stays valid JSON under `--json`; exit 0). `--json` keeps its
`{columns,rows}` shape. The no-owner conflict message names the lock and the socket
that did not answer, never "held by the daemon".

**3. Table output is sanitised.** `writeDBQueryTable` runs every header cell and every
value cell through `internal/sanitize.Text`; `--json` is unchanged.

**4. PRAGMA forms.** The paren form is allowed only for argument-taking names
(`table_info`, `table_list`, `index_list`, `index_info`, `foreign_key_list`,
`integrity_check`, `quick_check`); `journal_mode`, `page_count`, `page_size`,
`user_version`, `schema_version` are bare-only. `EXPLAIN` and `EXPLAIN QUERY PLAN`
followed by `PRAGMA` run the same check (so `EXPLAIN PRAGMA writable_schema = 1`,
`EXPLAIN PRAGMA user_version(7)` and `EXPLAIN QUERY PLAN PRAGMA schema_version(9)` are
`usage`). `EXPLAIN` of anything else is unchanged.

**5. `DB.Close` order.** Checkpoint (only a writable handle), close the pool, then
release the path handle and its flock, then notify `onClosed`; the handle is released
even if the pool close errors, and a second `Close` is a no-op.

**6. Read-only open and close.** Under the Turso build, `openReadOnly` refuses a file
whose header lacks the conversion marker (`application_id`, offset 68) with
`db.ErrNotConverted` — "relevo.db is not converted yet; start the daemon once" — and
`DB.Close` runs no `walCheckpoint` on a read-only handle. Under `-tags modernc` the
check is a no-op (modernc reads legacy files).

## Decisions this plan makes where the seed left the choice open

- **The `db query` marker is a handshake bit, not a per-request field.** `wire.Hello` gains `AdHoc bool`; the wire client sends it once per pooled connection from a new `client.Connector(sock, adHoc)`; `db.Options.AdHoc` and `db.DialContextAdHoc` build the pool from that connector; `cmd/relevo`'s `db query` uses `dialOwnerAdHoc` for both dials in `openDBQuery`. The field is additive and `wire.Version` stays 1: an old owner ignores it and simply never refuses; an old client never sends it. Only the request is refused, never the handshake: a refused dial would make `db query` fall back to a direct open, find the file held, and report the false lock conflict the previous round removed.
- **The reap request rides the existing upgrade hook, not an exec from the owner's goroutine.** The owner calls `OnAbandoned`; the daemon's hook logs once and sets an atomic flag; the existing upgrade hook (`daemon.go:410-445`) returns true on the next tick, so `Run` returns `ErrReexec` and the existing drain → listener handoff → `syscall.Exec` path (`daemon.go:449-472`) runs. Latency is the grace plus at most one daemon interval (2 s default). The owner keeps refusing ad-hoc reads until the exec ends the statement.
- **One registration, one hook call, one re-exec.** The tracker holds at most one abandoned statement and fires once per registration; the daemon sets its flag with a CAS and `Run` returns on the first true, so a loop is impossible. `Run` also checks its context before the upgrade hook, so no reap while the daemon is shutting down. The daemon wires the hook only when `reexecOK`; with re-exec unavailable the owner still refuses ad-hoc reads forever and the report says so (safe degradation).
- **The byte budget counts value bytes.** `onRow` adds a row's blob/string lengths (a small constant for other values) and stops before appending a row that would pass the budget, so an over-budget row is never printed and the read stops even when one value alone is larger than the budget. Row and byte caps share the existing stop signal.
- **The print seam is a nil-default writer var** (`dbQueryOut`, `os.Stdout` when nil), resolved at call time, so the existing `captureOutput` tests keep capturing and one test can stall the print.
- **`failWrap` folds the cause's own text into the message** when the formatted message does not already carry it. Collateral: the two `mastermind` not-found lookups and the owner-dial deadline line now end with their cause's text; no code, exit or `errors.Is` behaviour changes.

## Behaviour and its cases

**A. Abandoned statements are tracked, refused and reaped by re-exec.**

- *Detection.* `discardPinned` returns a channel closed when its rollback and discard finished. `(*conn).cleanup`, when that channel is still open after `discardTimeout`, registers it with the server as *the* abandoned statement (at most one: a second registration while one is live is dropped). The pin slot still returns immediately, exactly as today.
- *Grace.* `reapGrace` defaults to 30 s and is settable (`owner.SetReapGrace`, a test seam like `client.SetHandshakeTimeout`). If the channel closes first, the registration clears and no hook fires. If it is still open after the grace, the owner calls `OnAbandoned` once.
- *Refusal.* While a registration is live, any request on a connection that marked itself ad-hoc in the handshake is refused with the new `wire.RefuseReaping` ("the owner is ending a statement that will not stop; retry in a moment"). Connections without the marker — every normal relevo verb — are never refused. `db query` then prints `relevo: refused: db: query read-only: <message>` (exit 2) and does not fall back to a direct open, because its dial succeeded.
- *Reap.* The daemon's hook logs the reap and sets the flag; the next tick re-execs the daemon on its own binary through the unchanged drain/handoff/exec path, which ends the statement's thread. After the new image serves, `db query` works again; nothing is left to refuse.
- *Cases.* ends before the grace → ad-hoc reads resume, no hook; one request in flight when the statement abandons → that connection is the abandoned one, later ones are refused; normal verb during the window → served; daemon with re-exec disabled → ad-hoc reads refused, no re-exec.
- *Wording.* `RECURSIVE` stays refused as the cheap first line. `ErrRecursive`'s comment, `dbUsage`, the `db query` registry summary and the guide say plainly that it is not the guarantee: SQLite decides recursion structurally, so the owner's refusal and reap are what end a runaway statement.

**B. A byte cap in `db query`.** `--max-bytes` (default 16 MiB = `16777216`, refused below 1 as `usage`; a flag in `db`/`db query`'s registry rows, usage text and goldens). `onRow` adds each accepted row's value bytes, and when the row would pass the budget it is not appended, the cut is recorded and the read stops through the same `errQueryLimitReached` signal the row cap uses. After the read, `truncated at <budget> bytes (raise --max-bytes)` goes to stderr, exactly like the row note; stdout stays a valid table or `{columns,rows}` document and the exit stays 0. `zeroblob` values arrive as `[]byte` on both routes, so one over-budget value stops the read: on the owner route the client stops asking for the next batch, and nothing larger is ever sent.

**C. The lock is released before printing.** After the read finishes and before the truncation note or any row goes out, `cmdDBQuery` closes the handle (which releases the direct flock) and the deferred close becomes a no-op via a flag. A stalled stdout — a pipe nobody drains, `| less` then Ctrl-Z — can no longer hold `relevo.db.lock`, so the 12 s/15 s read-vs-open invariant holds for the print phase too. `--json` and the table share the writer seam.

**D. The `ErrNotConverted` hint is printed.** `failWrap` keeps its cause for `errors.Is` and now also carries the cause's own text into the message when the formatted text does not already contain it; the `db query` `ErrNotConverted` branch renders the cause's message, so the refusal ends `…relevo.db is not converted yet; start the daemon once`.

**E. `TestAWaitingOpenDoesNotBlockAnotherPath` is fixed.** The second path is created and migrated before the clock starts (then closed, so the flock is free), the shrunk wait is 5 s, and the assertion is ordering, not an absolute bound: after the pre-migrated second open returns, the first open must still be polling (`waited` empty); it then ends `ErrLocked`. The mutation the test exists for — the process-wide handle map held across the flock wait — still fails it, because the second open then queues until the first gives up and `waited` is already ready.
