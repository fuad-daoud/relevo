# Chains slice 1 · round 9 — the two-plan chain e2e and the round sweep

One-shot builder round. It starts from the branch where every earlier round of the slice (1-8, 5a, 5b) is
merged; it is the last round, and the slice lands as one PR. Commit, never amend. Ends with `make check`
**and** `make e2e` green.

## Deliverable

`make e2e` runs a two-plan local chain with the fake harness: plan 1 gets one `changes` verdict and one
correction round, plan 2 passes, the security phase finds one finding and its fix plan passes, the
chain finishes, the trace holds every step, and the MasterMind receives exactly one delivery — plus a
final sweep of the slice for leftovers.

## Pinned behaviour of the scenario

- `TestChainE2E` starts from the same isolation as `TestHeadlessE2E` (HOME/XDG dirs under a temp root,
  the fake `claude` first on PATH, `dbtest.InstallOwner`), registers a mastermind, and calls
  `relevo.ChainStart` with two plan files, `--security` on, actors that resolve to the fake harness.
- Daemon ticks (`NewDaemon(rt, 200ms)`) until the chain row is `done`, with a bounded deadline; each
  assertion below is checked after.
- The fake harness's builder rounds write a report and a commit; reviewer/planner/security rounds are
  reader rounds (the existing branch already handles a prompt naming an output file); the planner's
  final message is its correction or fix plan; the second reviewer round passes.
- Assertions: the trace has one row per transition and ends at finish; the builder got rounds 1, the
  correction, and plan 2; the reviewer saw the correction; `delivery.PendingForMasterMind` on each
  member is empty while the chain ran; exactly one pending `KindChain` entry exists, on the builder,
  and `relevo.WaitChain` returns it once with code 0; `show <n> --trace` renders the same steps.

## Tests, by name (what each pins)

`TestChainE2E` (the scenario above). Its helper `tickUntilChainFinishes` fails with the chain's row and
the members' notes when the deadline passes, so a stuck chain names the step.

## Mutation checks (design §12)

The e2e is the integration pin for all three mutations: with `changes` advancing to plan 2 the
correction round never runs (`TestChainE2E` fails on the trace); with `awaiting` matching any round
the trace gains a second row per close; with a missing verdict counted as a pass the first reviewer
round never runs. The unit-level names stay
`TestChainReviewerChangesSeedsCorrection`, `TestChainIgnoresACloseForAnotherRound`,
`TestChainReviewerCloseWithoutAVerdictHalts` (rounds 1 and 5a).

## Halt conditions

- If the fake harness cannot distinguish "reviewer, first round" from "reviewer, second round" from
  the prompt alone, halt and report; inventing a per-round marker in the production seed would be a
  design change, not a test fix.
- If `make e2e`'s pattern cannot be widened without changing what CI runs (`make check-test` runs the
  package anyway), halt and report rather than renaming tests to fit the old pattern.
- If the e2e cannot configure reader actors for planner/security through the existing shipped roles,
  halt and report the smallest config-file addition; do not ship new actors for the test only.
