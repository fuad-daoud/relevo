## The ruling on the tension (implement exactly)

**R1. `board` stays a peek verb.** `isPeekArgs` (`cmd/relevo/machinedb.go:114-131`) already returns true for `board` and every `board …` subverb, so `routeForArgs` gives `routeNone` and `captureAgyEnv` is skipped. The running board runtime never touches the database (it gets a scene path, a theme and a live dir; `internal/board` gains no db import). The verb never starts or waits for the daemon: no `ownerStartWait`, no `daemonStarter`. Update the `isPeekArgs` comment's flag list to `([path]/--board/--mastermind/--theme/--no-open)`.

**R2. Resolution is file-first; the database is read only when a name must be resolved.** An explicit path and an `mm_`/`pl_`/ULID id ref never open the database. A name ref or the single-registered fallback opens the registry read-only by the exact shape of `openDBQuery` (`cmd/relevo/db_query.go:264-300`): if `<state root>/relevo.db` exists, dial an already-running owner within the dial budget (`verbDialBudget`, start wait **0** — "short" means no start wait, not a smaller dial cap), else a direct read-only open (`openReadOnlyDB`, `cmd/relevo/wire.go:303-306`), else a refusal naming `--mastermind`/`RELEVO_MASTERMIND` (an `mm_` id needs no database). Build the registry as `&mastermind.DBRegistry{KV: db.TxKV{DB: d}}` (as `cmd/relevo/mastermind.go:88-93` does); never call `mastermind.Resolve`, whose `hit` writes `seen_at`.

**R3. A file-only resolution cannot fully satisfy §4, and the report says so.** Records are kv rows in `<state root>/relevo.db`; `<state root>/boards/` holds boards only, and no per-MasterMind file maps a name to an id. File-only therefore covers an explicit path (the path names the id) and an id ref; the name ref and the single-registered fallback need the read-only registry above. That is the minimum database contact and it stays before the server starts.

**R4. The spec's "no database" sentence needs a correction.** §9 says "board stays a peek verb: the pointer and the scene are plain files, and neither the database nor the daemon is touched." Corrected: "no database in the runtime; resolution is read-only (an id or a path opens no database at all)". The report quotes both; the spec file is **not** edited in this round.

**R5. The route test is the proof.** Extend the two existing route surfaces: the route table (`cmd/relevo/machinedb_wait_test.go:406-431`) gains `board` and `board url` rows (`routeNone`), and `cmd/relevo/machinedb_routes_test.go:173-221` (bugreport's proof) gains a board case: with a counting `daemonStarter` and no owner, resolving a name against a seeded db starts nothing, creates no `relevo.sock`, and leaves no db behind; resolving an `mm_` id succeeds with no db file at all.

## Settled rules (pin these)

**S1. Layout.** Live root `<state root>/boards/`, live dir `<state root>/boards/<mastermind-id>/`, scenes `<live>/<slug>.excalidraw` (one level; no nested dirs). Default scene name `board`. Pointer `<live>/current` (plain file, the scene name plus `"\n"`). `server.json` in the same dir. Live dir created 0700; pointer, `server.json` and scenes written 0600 through the existing atomic write (`internal/board/scene.go:114-141`).

**S2. `relevo board` resolution.**
- Explicit path: after `Clean`+abs against cwd, a path `<live root>/<id>/<name>.excalidraw` is live-shaped; the id is read from the path (file-only), the name must be a slug, and after `EvalSymlinks` on the deepest existing ancestor the path must still sit under `<live root>/<id>/` or the verb refuses. Otherwise the repo root is fetched (`boardRepoRootFn`, `cmd/relevo/board.go:49-62`) — its error is "not inside a git repository", usage exit 2 — and S1's `Resolve` (`internal/board/path.go:23-55`) classifies the path as repo; a path under neither is refused.
- `--board <slug>`: the live dir of the resolved MasterMind.
- No name: the pointer; if missing/empty, `board` and the pointer is written.
- `--mastermind <id|name>` → else `RELEVO_MASTERMIND` → else the single registered MasterMind → else usage naming the records; zero records names `relevo mastermind init`.
- `[path]` together with `--board`: usage refusal, exit 2.
- An explicit `--mastermind` naming a different id than a live path: usage refusal. Ambient `RELEVO_MASTERMIND` never overrides an explicit path; a repo path ignores `--mastermind`.
- Bare `relevo board` is the live board; the repo default scene is reached only by naming it (`relevo board docs/boards/board.excalidraw`).

**S3. Scene names are slugs** `^[a-z0-9][a-z0-9-]{0,63}$`; `--board`, the pointer and a live path's file must satisfy it.

**S4. Pointer rules.** Missing/empty file → default `board`; content that is not a slug → usage naming the file (never silently overwritten). Written when a live board is opened or selected and the name differs; `board url` never writes; a repo board never touches it.

**S5. Confinement.** S1's `EvalSymlinks` rule for both scopes, plus disjointness: when both roots are known, a live dir sitting under the repo root (or the repo root under the live dir) is refused — the scopes can never nest; the leak test is the reason.

**S6. `server.json`.** `{"scene","url","port","pid","started_at"}`, written after the listener binds, live boards only; removed on shutdown only when the file's `pid` and `started_at` still match ours (guard); a second server on the same board is allowed and the most recent writer wins; a stale file (dead pid) is ignored by readers and overwritten by the next writer; nothing else deletes it.

**S7. Liveness is the `mastermind.RecordState` pattern** (`internal/mastermind/state.go:14-29`): `started_at` is the board process's own start in Unix seconds (`procStartUnix`, `cmd/relevo/wire.go:527-533`); a pid that is dead, unmeasurable, or whose start differs means not live. A measurement failure at startup writes `0`, which readers treat as not live (the server still runs).

**S8. Statusline block.** `view.StatusLineDoc` gains `Board *StatusLineBoard` (`{"name","scope","url"}`, json `board`, null when absent) at the document top level beside `mastermind`, only for the calling MasterMind, filled for both `status --line` and `status --line --json`. It is present only when the pointer's scene equals `server.json`'s scene, the pid is alive and its start matches — a file read, a `server.json` read and a pid check, **no database read** (the id comes from the already-resolved record). `scope` is `"live"`. `--line` text renders `board <name> · <url>` dim, directly after the MasterMind line, truncated to the statusline width; `--line --json` carries the full URL. Any read error yields no block, never a failure.

**S9. `board url [--board NAME] [--mastermind M]`.** Scene = `--board`, else the pointer (never the default, never written). Prints `server.json.url` with its token when S8's liveness holds; otherwise exit 1 `not_available`, nothing on stdout, one line naming the scene and the MasterMind. It is read-only: no pointer write, no db write, no listen.

**S10. Repo boards keep S1 semantics exactly:** named path, theme, svg companion, no `server.json`, no pointer.

## Deleted behaviour (closed list)

1. Bare `relevo board` opening the repo scene `docs/boards/board.excalidraw`; it now opens the live `board`, and `TestBoardRefusesOutsideRepo`'s bare call is rewritten (an explicit path keeps the outside-repo refusal).
2. The blanket "outside a git repository is usage" refusal for every board invocation; it now applies only to an explicit path that is not live-shaped.
3. Nothing else is removed: no verb, flag, registry row or golden is deleted (three goldens are rewritten to carry `"board":null`), and `board.DefaultScene` / `Resolve`'s empty-arg repo default stay in place, now CLI-unreachable — the report flags them as a later cleanup.

## Mutations the report must show (each fails a named test, then is reverted)

1. Skip `EvalSymlinks` in the live/repo confinement → the two symlinked-parent cases fail.
2. Drop pid liveness in `LiveURL` (present whenever `server.json` exists) → the dead/reused-pid case fails.
3. Flip the resolution order (pointer before `--board`, or db before a live path) → the precedence case fails.
4. Introduce a cross-scope leak (accept a live-shaped path that resolves under the repo root, or drop the disjointness refusal) → the leak/overlap case fails.
5. Drop the shutdown guard in `RemoveServerInfo` → the "remove A leaves B" case fails.
