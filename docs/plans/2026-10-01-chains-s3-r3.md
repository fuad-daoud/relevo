## Preamble

### Where the seed and the code disagree (verified at `0ac52a80`)

1. **The base bundle does not travel at create today.** The seed says `POST /v1/chains` carries "the base bundle `bind --server` ships". But `bind --server` sends no bundle when it creates. The bundle goes with the first `StartRound`: it is absorbed in `serve/rounds.go:210-216`, and the server worktree is cut from it in `syncRoundWorktree` at `serve/rounds.go:262-273`.
   - So `POST /v1/chains` must be a multipart request: a `chain` JSON field plus a `bundle` file, built by the same `Transport.Snapshot` that `remoteShip` uses (`remote_send.go:83-92`).
   - The server cuts the builder's worktree when it creates the chain.

2. **"Several closed, unacked rounds" is only half there.**
   - Round files for any round up to `ClosedRound` are served (`serve/roundfiles.go:115,131`).
   - But the view's closed-round facts are only for `ClosedRound` (`relevo/served.go:99-160`), and the bundle route serves only `n == ClosedRound` (`roundfiles.go`, `handleRoundBundle`).
   - The client's catch-up assumes a member is never more than one round behind (slice 2's global halt condition). It installs only `view.ClosedRound` (`remote_sync.go:345-356`, `remotefetch.go:557`).
   - So a server-chain member must skip the per-binding catch-up. It needs its own pull, and that pull needs per-round facts for older rounds, carried on the chain view.

3. **The same daemon drives the chain, but its sends bypass the builder cap.** `serve.Tick` runs `relevo.NewDaemon(...).Tick` per owner (`serve/daemon.go:35-40`), so `chainApply`/`chain.Next` already run on the server. But `sendChainRound` calls `startRound` directly (`relevo/chain_send.go:83`). That bypasses `serve.max_builders` and `admit` (`serve/admit.go:100`).
   - Fix: a served member's chain round must defer (set `QueuedAt`, the shape `Send(Defer)` uses at `send.go:545-649`), so `admit` starts it.

4. **A reader can share the builder's tree on the server, with one gap.** I checked whether a remote reader member can run on the builder's tree.
   - **It works mechanically.** A reader whose `CWD` is the builder's served worktree runs in a scratch tree made from that worktree: `sendChainRound` captures the baseline from `CWD`, and `Admit` builds the scratch (`queue.go:58`, `scratch.go:69`). That is exactly how local chains work.
   - **The gap:** today's served readers each get their own worktree and branch (`serve/bindings.go:221-249`). A reader with no branch would break two things:
     - `closeServedRound` (`relevo/served.go:44-82`) needs the binding's own branch and worktree. A reader without them never records `ClosedRound`, so it is never pulled and the artifact routes stay shut.
     - `teardownServed`/`releaseServedRefs` (`serve/cleanup.go:103-132`) would remove whatever worktree and branch the record names.
   - **Smallest fix (round 2):**
     - Reader members carry an empty `Worktree` and `Branch`, with `CWD` set to the builder's worktree.
     - `closeServedRound` records a branchless reader's `ClosedRound` with no git facts.
     - Teardown skips an empty `Worktree` and `Branch`.
     - The bundle route refuses a branchless binding.

5. **`chainTerminal` would queue the end delivery on a server member.** It calls `delivery.Queue` on the carrier (`relevo/chain.go:494-516`), and on the server that member has no MasterMind. On a served carrier (`Owner != ""`) it must queue nothing; the client queues its own delivery after it pulls.

6. **The verb has no `--server` today.** There is no flag (`cmd/relevo/chain.go:50-75`) and no `ChainOptions.Server` (`relevo/chain_start.go:25-62`).
   - `chain_start.go` is 599 lines, so the round that adds the dispatch first moves three helpers out (file cap 600).
   - `chain.go` is 586 lines, so its edits are calls to helpers that live in new files.

7. **Resume `--gate` works on a server chain.** On the server the builder is local, so slice 2's `resumeRemoteGateRefusal` does not apply there. The client sends the command it resolved, and an explicit gate always wins in `resolveGateFor`.

8. **A chain's name is never reusable.** `chainFreeNames` refuses any existing chain row, done or not (`chain_start.go:397-414`). The plan relies on this: if the server accepts a chain but the client fails to record it, the fix is to re-run the same command. The server answers an identical retry with 200 and the chain's current view, so the client can record it.

### Open questions (the plan's default comes first; say if you want otherwise)

- **Delivery when a chain is stopped.** The seed says the end delivery is queued "once the chain is finished or halted". Spec §9.2 and local chains (`chain_verbs.go:80-101`) also deliver on `stopped`. The plan delivers on all three terminal statuses, for parity.
- **Upper bounds on untrusted fields.** These are my choices, each a named constant:
  - 64 plans per chain, 1 MiB per plan;
  - `max_corrections` ≤ 20;
  - `regate` ≤ 10.
- **Repair rounds skip the server queue.** A server chain's builder repair round, opened after a red gate by the headless repair arm (`headless.go:1143-1153`), starts at once outside the queue. That is how any served repair would start. The plan leaves it as is.

### Pinned behaviour

- **Owner scope.** Every chain route resolves through the caller's own store. Another owner's chain is 404 on GET, stop, resume and done, and a create with the same name under another owner is allowed.
- **Validation runs before anything exists.** No bare repo, ref, worktree or row exists until every field and the preflight have passed. A refused create leaves none of them.
- **The bundle must contain the base.** A bundle whose out ref does not resolve to `base_commit` is refused, and nothing is created.
- **Retries.** An identical retry returns 200 with the current view and creates nothing. A different request under the same name is 409.
- **The other verbs.** stop, resume and done act through the same `relevo` verbs a local chain uses. A resumed or stopped round re-enters the queue through `admit`.
