## The slice's decisions (the spec's assumption is false)

The spec says "Sending a seed to a remote member is an ordinary remote `send`" and "the local daemon sees a remote member's close through its existing remote sync … and that close is the chain's event" (§7). Both are false as written, and the fix belongs here:

- **D1 — the send needs a pending-send step.** `sendChainRound` is local-only, and `sendRemote` both refuses a running chain's member and must not run inside the chain's critical section (a 10-minute socket under a 90 s flock). So the chain stages the round's text under the lock, records the transition + trace, and a new step (`chainSendPending`, called outside any lock from the daemon tick, `SyncRemote`, `ChainStart` and `ChainResume`) ships it, then records the member's round under a short lock. The server's identical-plan retry (`serve/rounds.go:112-127`) makes the step idempotent. A send to a remote member is *staged* wherever a local send would be *started*, from plan 1 to every later plan, correction and repair.
- **D2 — the check must run where the tree is.** A served binding runs no gate, so the chain's remote builder would have no check at all. The create request gains the chain's resolved gate command (`Settings.Gate`); the server stores it and runs it at close; the view ships `gate_result` and a `gate` round-file route, and catch-up pulls the log to `rt.Store.GateLogPath(name, n)` before the reviewer is seeded. The server's `Regate` stays 0: the repair is the chain's, exactly as slice 1's wiring owns a local member's red gate.
- **D3 — one new server feature.** `remote.FeatureChainMember = "chain_member"` means: a create may name a gate and the server runs it; the view reports the closed round's gate result; the round-file route serves the gate log; the round form honours `verify`. A chain-member placement that a server cannot carry is a *skip* in the actor's placement list (the `placementFlags` model), and an actor whose list leaves no viable entry refuses the start. The token is needed even when the chain's gate is empty, because D7's `verify=0` is what keeps the server from opening its own consult on a member round.
- **D4 — readers are local.** A chain's reader members share the builder's tree by path; a remote reader's seed would name paths that exist on another machine. So a reader's placement list is walked with servers skipped (a named reason), never probed; a reader runs on this machine and reads the pulled copies (report, diff, gate log) plus the chain's own plan copy. This narrows §7's "each member binds where its actor's placement puts it" for readers only, which §8 already allows ("a gap is fixed separately and picked up"). The only remote member slice 2 supports is the builder.
- **D5 — the close carries the stop.** `applyCatchUpReport` must pass `stopped = a.View.Stopped != ""`, or a stopped remote round halts the chain instead of stopping it.
- **D6 — merged by #773.** `chainSeedView`/`chainRoundGate` already fill the seeds' check fields on both the close and the resume paths; this slice adds nothing there, and round 3 relies on the merged helper when it puts the remote close's record on the report entry.
- **D7 — remote rounds are verify-free.** The chain's remote send passes `verify=false` on the round form; the server passes it through (`SendOptions.Verify`).
