## Part 2 — #1351 part 2: finding and consistent rule

Finding the builder must first establish from code (stated here so the round does not re-derive it): `--param` on a server-chain resume IS applied on the server. The chain is `client chainServerResume` (`internal/relevo/chain_server_view.go` 205-244, forwards `opts.Params` at 224) to server `resumeOptionsFromWire` (`internal/serve/chains_resume.go` 43-89, merges `req.Params` at 82 into `opts.Params`) to `ChainResume` to `chainResumeWorkflow` (`internal/relevo/chain_resume_wf.go` 26-136, merges flag params with `opts.Params` at 75-81, `workflow.WithParams` at 83) to `chainResumeLocked` to `chainResumeAddMembers`/`chainResumeSyncMembers` (`internal/relevo/chain_resume_swap.go` 258-282) to `validateServedSwapActors` (71-88, server-side `servedActorPick`) and `applyServedSwaps` (111-130). Hence `--param builder=builder-qwen` swaps the builder actor and the server re-picks from that actor's list; the observed `glm-5.3-flash-free` run is the swap applied with the fallback candidate picked, not a dropped param. Because it applies, the start must accept it consistently where the wire can carry it.

Consistent rule: `chain --server --param` is accepted when the server can carry it and refused with the existing message when it cannot. The server path already parameterizes the definition client-side (`internal/relevo/chain_server_start.go` `chainServerResolve` 90-111 via `chainParamsFor` in `internal/relevo/chain_params.go` 35-79, which already merges `opts.Params` last) and ships it as Workflow JSON when the server advertises `FeatureWorkflow` (`chainServerRequest` 338-359; gate at 161-167). The legacy settings-only wire (`req.Settings`) cannot carry arbitrary params, and the served legacy definition (`servedChainDefinition` in `internal/relevo/chain_served_wf.go` 15-40) fixes the builder actor. So: the CLI (`cmd/relevo/chain.go` 195-201) stops refusing `--param` unconditionally (keeps refusing `--workflow`/`--task`/`--from` with `--server`); `chainServerResolve` refuses `--param` with the existing "server's workflow feature is not available yet" wording when the server lacks `FeatureWorkflow`, and otherwise lets it flow through the existing `chainParamsFor`/`WithParams`/Workflow-JSON path. The resume path is unchanged. The report documents the remaining asymmetry: starting a chain on a pre-workflow server still refuses `--param`, while resuming such a chain applies it, because the server holds the definition.
