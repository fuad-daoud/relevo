# Chains slice 2 · round 2 — the start places its builder; the pending-send step ships its rounds

One-shot builder round. Starts from the branch as round 1 left it. Commit, never amend. Ends with `make check` green. Focused loop: `go test ./internal/relevo/ -run 'TestChainStart|TestChainSendPending|TestChainResume' -count=1`.

### Deliverable

A chain start resolves every member's placement the way `bind --actor` does. A builder whose actor names a server is created there (all-or-none with every local side effect) with the chain's own resolved check on the create; the readers stay local and read its artifacts, and a new step outside the state lock ships every round the chain stages for the remote builder — plan 1, later plans, corrections and repairs alike. `ChainResume` uses the same step, and every send to a remote member goes through the one start-or-stage helper.

### Pinned behaviour

- **Reader rule.** A reader member's placement list is walked with every server entry skipped, no probe; a local entry is viable when `resolveRole` succeeds; no list keeps today's local path; a list with no local entry refuses the start with `placementError`'s one line, naming every skip. A reader is never remote in this slice and carries no gate.
- **Builder rule.** The builder's list is walked exactly as `bind --actor` does: the chain verb has no `--server`, so the actor's list decides; a server without `chain_member` or any feature the member needs is a skip with its reason; no viable entry refuses the start with `placementError`'s one line, naming every skip.
- **The check is the chain's.** The member's `Gate`/`Regate` and the create request's `Gate` come from the resolved `Settings` (#773), so a policy `gate.default` travels with no flag at all, `--no-gate` sends "", and a stored setting is what a resume reads back. `Regate` stays client-side: the wire has no field for it and the chain owns the repair.
- **All-or-none.** Order of side effects: read-only preflight (everything above) → server create → local branch → `Tx.CreateChain` (all member rows and the chain row, one transaction) → plan copies → plan staging → the send step. A failure after the server create unbinds it on the server first and then deletes the branch; a failed server create has no local side effect to undo (nothing local exists before it). A rollback failure is joined into the returned error, naming what could not be removed.
- **The member record** is exactly `addRemote`'s: `Builder.Endpoint{Mode: remote, Server, Kind, AgentName}`, `BuilderCandidate: view.Candidate`, `Tier: view.Tier`, `Shape: view.Shape`, `Link: remoteLink(view)`, `RecordID`, mastermind endpoint, feature/ticket, `Role` and `Gate`/`Regate` from the chain's resolved settings, `Round:1`, `State: active`.
- **The create request** carries the gate (the chain's resolved `Settings.Gate`), the chain's role/labels and the author; the client maps its candidate token with `serverCandidate`/`serverTokenFor` and refuses with the same one line when there is no match.
- **Readers' tree.** A local builder keeps today's readers (CWD = builder worktree). A remote builder gives every reader `CWD = the chain's repo` (the chain's own checkout) and no worktree/branch; `Repo`/`RepoRef` stay the chain repo's.
- **The pending-send step.** `chainSendPending(ctx, rt)` (unlocked) walks the running chains; for a chain whose `AwaitingMember`'s binding is remote, whose member has no prompt log entry for `AwaitingRound`, and whose staged prompt file `PromptPath(member, round)` exists, it ships that file in one `remoteShip` and then, under a short `WithLock`, re-checks the state (chain still running, still awaiting, no entry yet), writes the member's prompt entry, `LastShipped`, `RemoteStatus`, `RoundStartedAt`, `State active`, and saves. A second concurrent or repeated run is a no-op (no entry) or an identical-plan retry the server dedupes. A member in NEEDS YOU, a missing staged file and a non-remote member are skipped silently.
- **A failed ship** takes the same short lock, writes the member `State: needs_you`, `Halt: "builder send failed: <err>"`, and halts the chain with `chainSweepHalt`'s shape and the reason `member <name> could not start: <err>` — one trace row, one delivery. That outcome is recorded, not returned: `ChainStart`/`ChainResume` report a step error only when the store write itself failed, wrapped as the existing plan-1 failure is (`chain_start.go:246`).
- **Plan 1** is staged from the chain's plan copy before the send; the chain row is running and awaiting the builder before the step runs, so a crash between the two is repaired by the next tick's step.
- **Resume** for a remote builder stages the resumed round like any send and lets the step ship it; a failed ship halts the chain as above.

## The slice's decisions (the spec's assumption is false)

The spec says "Sending a seed to a remote member is an ordinary remote `send`" and "the local daemon sees a remote member's close through its existing remote sync … and that close is the chain's event" (§7). Both are false as written, and the fix belongs here:

- **D1 — the send needs a pending-send step.** `sendChainRound` is local-only, and `sendRemote` both refuses a running chain's member and must not run inside the chain's critical section (a 10-minute socket under a 90 s flock). So the chain stages the round's text under the lock, records the transition + trace, and a new step (`chainSendPending`, called outside any lock from the daemon tick, `SyncRemote`, `ChainStart` and `ChainResume`) ships it, then records the member's round under a short lock. The server's identical-plan retry (`serve/rounds.go:112-127`) makes the step idempotent. A send to a remote member is *staged* wherever a local send would be *started*, from plan 1 to every later plan, correction and repair.
- **D2 — the check must run where the tree is.** A served binding runs no gate, so the chain's remote builder would have no check at all. The create request gains the chain's resolved gate command (`Settings.Gate`); the server stores it and runs it at close; the view ships `gate_result` and a `gate` round-file route, and catch-up pulls the log to `rt.Store.GateLogPath(name, n)` before the reviewer is seeded. The server's `Regate` stays 0: the repair is the chain's, exactly as slice 1's wiring owns a local member's red gate.
- **D3 — one new server feature.** `remote.FeatureChainMember = "chain_member"` means: a create may name a gate and the server runs it; the view reports the closed round's gate result; the round-file route serves the gate log; the round form honours `verify`. A chain-member placement that a server cannot carry is a *skip* in the actor's placement list (the `placementFlags` model), and an actor whose list leaves no viable entry refuses the start. The token is needed even when the chain's gate is empty, because D7's `verify=0` is what keeps the server from opening its own consult on a member round.
- **D4 — readers are local.** A chain's reader members share the builder's tree by path; a remote reader's seed would name paths that exist on another machine. So a reader's placement list is walked with servers skipped (a named reason), never probed; a reader runs on this machine and reads the pulled copies (report, diff, gate log) plus the chain's own plan copy. This narrows §7's "each member binds where its actor's placement puts it" for readers only, which §8 already allows ("a gap is fixed separately and picked up"). The only remote member slice 2 supports is the builder.
- **D5 — the close carries the stop.** `applyCatchUpReport` must pass `stopped = a.View.Stopped != ""`, or a stopped remote round halts the chain instead of stopping it.
- **D6 — merged by #773.** `chainSeedView`/`chainRoundGate` already fill the seeds' check fields on both the close and the resume paths; this slice adds nothing there, and round 3 relies on the merged helper when it puts the remote close's record on the report entry.
- **D7 — remote rounds are verify-free.** The chain's remote send passes `verify=false` on the round form; the server passes it through (`SendOptions.Verify`).

## Global halt conditions (any round)

- If `remote.FeatureChainMember`'s server half cannot be shipped additively (a client's create with a gate breaks an old server's parse), halt: the plan promises an old server ignores the field.
- If a serviced binding turns out to run its own repair rounds (`Regate` filled by a policy the plan missed), halt — the chain would double-repair.
- If a remote member's close can be collected with `view.ClosedRound > b.Round` in any reachable flow, halt and report; the plan relies on the client driving every send, and the guard must then be designed, not guessed.
- If the reader-locality rule contradicts a test or a surface that cannot be changed in the round's scope, halt and report the file.
- If #772 (member guards) lands before a round starts and moves a seam this plan cites above its citation, re-verify the citation first; halt if it moved into a file the round's scope excludes.
